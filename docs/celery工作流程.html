1. 一句话本质

Celery 的核心思想就一句：把「在 Web 进程里起线程执行」换成「往消息队列里投递一条任务消息，由独立的 Worker 进程去消费执行」。

Web 进程只负责「投递 + 立即返回 task_id」，真正干活的是另一批进程（可以在别的容器、别的机器）。中间靠 Redis 当消息队列把两端解耦——这就是「生产者 / 消费者」模型。

7. 为什么 Celery 要用 Redis（而不是别的）

Redis 当 Broker 的原理

Redis 的 List 结构天然就是一个轻量消息队列：

  • 生产者：LPUSH queue task_message —— 把任务消息塞进队列头部
  • 消费者：BRPOP queue 0 —— 阻塞式从尾部弹出，队列空就挂着等，有消息立刻拿到

这一进一出，就把「进程内直接起线程」变成了「跨进程 / 跨机器投递」——这正是解决「不能横向扩展、重启丢任务」的根本。

Redis vs RabbitMQ 怎么选

RedisRabbitMQ
定位轻量、简单、快专业消息中间件，功能全
路由能力简单队列复杂路由 / 优先级 / 死信 / 确认
运维成本低较高
额外收益还能当缓存（你阶段1的检索缓存正好用它）无
结论：对 ResumeAgent 这个量级，Redis 足够，而且一次引入、两处复用——既做 Celery 的 Broker/Backend，又做阶段1的检索结果缓存。这就是「Redis 接入和 Celery 一起做」的合理性所在。RabbitMQ 属于「需要复杂路由 / 强可靠投递」时才上，本项目用不到。
