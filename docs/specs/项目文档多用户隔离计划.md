# 项目文档多用户隔离 实施计划

> 状态：待实施 ｜ 依赖文档：`docs/specs/api-contract.md`（接口契约）、`docs/用户系统交付说明.md`（鉴权体系）

## 1. 背景与目标

项目最初是单用户设计，知识库全量共享。接入多用户后：

- **课程知识**（`course_pdfs` 解析产物）：公共资源，保持全局共享，**本次不动**。
- **项目素材**：目前是 `project_highlights/`（入库检索）+ `project_intros/`（全文引用）两个全局目录，所有用户共享 → **必须按用户隔离**。
- **已上传简历**：已通过 `build_tasks.user_id` 隔离，作为本次的参考范式。

同时解决两个既有问题：

1. 项目亮点与项目介绍内容高度重合，用户需维护两份文档 → **合并为单一文档模型**。
2. `make_doc_id()` 只哈希项目名，多用户下同名项目 doc_id 撞车互相覆盖 → **doc_id 引入用户维度**。

### 已确认的设计决策

| # | 决策 | 结论 |
|---|---|---|
| 1 | 向量库选型 | **保留 FAISS**，不引入 pgvector（见 §10 风险说明） |
| 2 | 用户隔离方式 | PG 表存 `doc_id → user_id` 映射，检索时转 `doc_ids` 白名单下传 |
| 3 | 文档模型 | 亮点 + 介绍**合并为单一项目文档**，`projects/` 单目录 |
| 4 | `## 简历描述` 章节 | **强制约定**，缺失时降级为全文引用 |

## 2. 数据模型

### 2.1 目录布局

```
data/knowledge_base/projects/
├── *.md                # 公共素材（user_id = NULL），CLI 流程沿用
└── u{uid}/*.md         # 用户私有文档，Web 上传落点

data/processed/course_chunks/
├── <hex>.json                    # 课程分块（公共，不变）
├── project-<hash12>.json         # 公共项目分块（兼容现有 26 份）
└── project-u{uid}-<hash12>.json  # 用户私有项目分块

data/databases/vector_dbs|bm25_dbs/     # 索引文件名随之带 u{uid} 段
```

**目录保持扁平不分子目录**：`VectorRetriever._load_dbs()` 用 `documents_dir.glob("*.json")`
（非递归），分层目录会打破现有约定。用户维度靠**文件名前缀**而非目录层级表达。

**公共文档 doc_id 不加 user 段**：现有 26 个 `project-<hash>.json` 无需重命名即天然成为公共素材，迁移成本最低。归属判定的权威源是 DB 表，不是文件名。

### 2.2 新增模型 `ProjectDoc`

**不手写 DDL**。SQLAlchemy 模型是 schema 的唯一真理来源，建表与索引由 alembic autogenerate
产出。在 `src/database/models.py`（文件末尾，`RefreshToken` 之后）新增：

```python
class ProjectDoc(Base):
    """项目文档（合并后的亮点/介绍）与用户的归属映射"""
    __tablename__ = "project_docs"
    __table_args__ = (
        # user_id 为 NULL 时（公共素材）不参与普通 UNIQUE 比较，需按区分别建部分唯一索引
        Index("uq_project_docs_user_name", "user_id", "project_name",
              unique=True, postgresql_where=text("user_id IS NOT NULL")),
        Index("uq_project_docs_public_name", "project_name",
              unique=True, postgresql_where=text("user_id IS NULL")),
    )

    id: Mapped[int] = mapped_column(Integer, primary_key=True, index=True)
    doc_id: Mapped[str] = mapped_column(String(64), nullable=False, unique=True, index=True)
    user_id: Mapped[int | None] = mapped_column(
        ForeignKey("users.id", ondelete="CASCADE"), nullable=True, index=True)
    project_name: Mapped[str] = mapped_column(String(200), nullable=False)
    file_name: Mapped[str] = mapped_column(String(200), nullable=False)
    source_path: Mapped[str] = mapped_column(Text, nullable=False)
    tags: Mapped[list] = mapped_column(JSON, nullable=False, default=list)
    has_resume_section: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False)
    mtime: Mapped[float | None] = mapped_column(Float, nullable=True)
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), default=lambda: datetime.now(UTC))
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), default=lambda: datetime.now(UTC),
        onupdate=lambda: datetime.now(UTC))

    owner: Mapped[User] = relationship(back_populates="project_docs")
```

`models.py` 顶部 import 需补 `JSON` / `Index` / `text`；`User` 侧补
`project_docs: Mapped[list[ProjectDoc]] = relationship(back_populates="owner", cascade="all, delete-orphan")`
（文件已有 `from __future__ import annotations`，前向引用可延迟解析）。

| 字段 | 用途 |
|---|---|
| `user_id = NULL` | 公共素材，所有用户可见 |
| `has_resume_section` | 是否含 `## 简历描述`；`false` 时简历生成降级全文引用（列表页提示用户补充） |
| `tags` | 原 `metainfo.tags`，含「简历优先」用于定向检索 |
| `mtime` | 沿用现有增量判断（源文件 mtime 比对） |

**为何用部分唯一索引**：同用户下项目名不可重复（重复即视为覆盖更新）；而公共素材
`user_id` 为 NULL，PostgreSQL 中 NULL 不参与 UNIQUE 比较，普通唯一约束拦不住公共区重名，
故按 `user_id IS (NOT) NULL` 分两个区各建一条部分唯一索引。

`ondelete="CASCADE"` 而非 `BuildTask` 用的 `SET NULL`：项目文档是用户私有数据，删号即应删除。

> **删号必须联动清理文件**：DB 行靠 FK `ondelete="CASCADE"` 级联删除，但源文件、
> chunks JSON、faiss、pkl 四类文件不在 DB 管辖内，必须在删除用户前显式清理，见 §4.7。

### 2.3 迁移：交给 alembic autogenerate

`alembic/env.py` 已 `import src.database.models` 且 `target_metadata = Base.metadata`
（L9 / L30），模型定义好即可被检出。`alembic.ini` 的 `sqlalchemy.url` **留空**，连接串由
`env.py` L14 从 `.env` 的 `DATABASE_URL` 读取。

`.env` 已指向 db 容器映射到宿主的端口（`postgresql+psycopg://...@127.0.0.1:5433/resumeagent`），
**宿主直接跑即可，无需 `docker compose exec`**：

```bash
python -m alembic revision --autogenerate -m "add project_docs"
python -m alembic upgrade head
python -m alembic current          # 确认已到 head
```

> 两点注意：
> 1. **PowerShell 假报错**：alembic 的 INFO 日志走 stderr，PowerShell 会判为错误并置
>    `ExitCode=1`，以 stdout 输出的版本号为准（README「PowerShell 假报错」条目）。
> 2. `env.py` L89-92 已为 win32 切 `WindowsSelectorEventLoopPolicy`，宿主跑异步迁移无障碍。
>    当前库状态已验证：`python -m alembic current` → `023db0559c78 (head)`。

> **必须人工核对的部分**：autogenerate 对带 `postgresql_where` 的部分索引检测支持不完整，
> 生成的 `op.create_index()` 可能丢失 where 子句——典型症状是此后每次 autogenerate 都重复
> 检出同一个"差异"。生成后打开迁移文件核对，缺失则手工补：
>
> ```python
> op.create_index("uq_project_docs_user_name", "project_docs", ["user_id", "project_name"],
>                 unique=True, postgresql_where=sa.text("user_id IS NOT NULL"))
> op.create_index("uq_project_docs_public_name", "project_docs", ["project_name"],
>                 unique=True, postgresql_where=sa.text("user_id IS NULL"))
> ```
>
> `downgrade()` 内对应的 `op.drop_index` 用 `op.f("...")` 包裹索引名（对齐现有迁移写法）。
>
> 另需核对 `ondelete="CASCADE"` 是否生成为
> `sa.ForeignKeyConstraint(["user_id"], ["users.id"], ondelete="CASCADE")`。

**类型选择说明**：`tags` 用 `sa.JSON` 而非 `postgresql.JSONB`——本期不做 JSON 内部查询
（`list_tagged_project_ids()` 仍走 chunks 文件扫描），保持可移植性即可；后续若要按 tag
做 SQL 层过滤（`WHERE tags @> '["简历优先"]'`）再换 JSONB + GIN 索引。

## 3. 文档格式约定

合并后的单一项目文档结构：

```markdown
# 项目名                      ← 必需，项目名唯一来源

> 标签：简历优先               ← 可选，可多个（、/,/，分隔）

## 一句话简介                  ← 建议，供 LLM 挑选目录用
一句话概括项目

## 简历描述                    ← 强制约定，简历生成引用区
精炼的简历措辞成品，可直接放进简历

## 技术栈                      ┐
## 项目难点                    ├─ 分块入库，供知识问答检索
## 量化成果                    ┘
```

**两种消费方式（一份文档，两种取法）**：

| 用途 | 取用范围 | 对应原路径 |
|---|---|---|
| 简历生成 | `## 简历描述` + `## 一句话简介` | 原 `project_intros` 全文引用 |
| 知识问答 | 全部 `##` 章节分块入库检索 | 原 `project_highlights` |

章节标题匹配沿用现有兼容变体风格（参考 `ProjectDocParser.extract_summary`）：

```python
_RESUME_TITLE_PATTERN = re.compile(r"^##\s*(简历描述|简历表述)\s*$", re.MULTILINE)
```

> 实施时**收窄了匹配范围**：初版纳入的「项目描述」已移除——它太通用，亮点文档常拿它当
> 项目概述，一旦误匹配，简历只会引用这一节而丢掉真正想表达的措辞。只认明确带「简历」
> 字样的标题，匹配不上就走全文降级，比误匹配安全。

**降级规则**：无 `## 简历描述` 章节时，取全文（去掉标签行）作为简历素材，并在日志与列表
接口中标记 `has_resume_section=false` 提示用户补充。

### 4.3 检索器刷新（关键）

`VectorRetriever.all_dbs` 是**构造时全量加载的快照**（`retriever.py` L178），新文档入库后
进程内单例不可见。且 Celery worker 与 API 是**不同进程**，worker 里刷新刷不到 API 进程。

**方案：API 侧懒刷新（版本号比对）**，不引入 pub/sub：

1. `VectorRetriever` 增 `refresh(doc_ids: list[str])`：仅加载/替换指定 doc 的 faiss 索引，不重建全量。
2. `BM25Retriever` 增 `invalidate(doc_id)`：清该 doc 的 `_doc_cache` / `_index_cache`（L53-54）。
3. `AgentTools` 增 `sync_project_docs(user_id)`：按 `MAX(updated_at)` 与进程内记录的版本比对，
   有变化才刷新。
4. 调用时机：每次对话开始时（`chat.py` 在 `run_stream` 前）调一次，成本是一次轻量索引查询。

优点：天然支持多 worker（各进程自行比对），无需消息基础设施；文档变更低频，绝大多数请求无开销。

### 4.7 文件清理（删号 / 删单文档共用）

一个项目文档在磁盘上占 **4 处**，DB 只管 `project_docs` 行，其余必须显式清理：

| # | 路径 | 说明 |
|---|---|---|
| 1 | `projects/u{uid}/{file_name}` | 源 md |
| 2 | `course_chunks/{doc_id}.json` | 分块 |
| 3 | `vector_dbs/{doc_id}.faiss` | FAISS 索引 |
| 4 | `bm25_dbs/{doc_id}.pkl` | BM25 索引 |

抽一个统一函数（供删号与删单文档复用）：

```python
def purge_project_doc(doc: ProjectDoc) -> None:
    """删除单个项目文档的全部落盘产物 + 检索器失效"""
```

**删号联动**（改造 `src/api/routers/auth.py` 的 `DELETE /auth/{user_id}`，现 L307-328）：

1. 删除用户**之前**先查出其全部 `ProjectDoc`（行删了就没 `doc_id` 了）
2. 逐个 `purge_project_doc()`
3. 兜底 `shutil.rmtree(projects/u{uid}/)` —— 清理上传了但入库失败/未入库的残留
4. 触发 `AgentTools` 检索器失效
5. 再删用户（DB 行由 FK CASCADE 级联）

**删除失败的处理**：文件清理失败**不阻塞删号**（避免用户删不掉账号），但记 `error` 级日志
便于排查，残留由 `prune` 兜底。删除顺序上先文件后 DB 行，反向会导致孤儿文件无法溯源。

**异步路由注意**：`DELETE /auth/{user_id}` 是 `async def` + `AsyncSession`，文件 IO 是同步阻塞的。
单用户文档数有上限（≤30）、文件小，直接同步删可接受；若实测有感知，改用
`fastapi.concurrency.run_in_threadpool` 包裹清理调用。

### 5.1 模板下载端点

返回 JSON 而非 `FileResponse`：文件名由后端给定（中文友好，不必处理
HTTP header 里中文 `filename` 的编码兼容），前端用 Blob + `a[download]` 触发保存。

由此形成闭环，三处共用同一份 md 文件：

```
templates/project_doc_template.md
   ├── GET /api/project/template  → 用户照着写
   │                                    ↓ 上传
   ├── matches_template()          → 合模板？直接入库（不调 LLM）
   └── build_system_prompt()       → 不合？按同一份模板重写
```

**核心承诺**：照模板填写的文档**不会被大模型改写**。已由测试闭环保证——
`test_content_is_the_validation_baseline` 断言模板本身能通过 `matches_template()`，
若有人往模板里加了不符合自己规则的章节，该测试立即失败。

**新建任务类型**：`build_tasks.task = "ingest-project"`（与既有 `"parse-resume"` 并列）。

## 8.5 上传预处理与预览确认（阶段 4 之后的增补）

起因：用户上传的项目文档格式常与后端约定不一致。实测 7 种输入后发现后果分两级：
无一级标题 → **任务直接 failed**；有标题但无章节/`###` 分节/表格为主 → **静默降级**
（上传成功但整篇塞进一块，检索质量差且用户无从察觉）。

### 8.5.1 最终形态：模板即标准（现行）

单一真理来源 —— `src/knowledge/templates/project_doc_template.md`。同一份文件同时充当：

| 角色 | 用途 |
|---|---|
| 用户下载填写的空白模板 | 后续 `GET /api/project/template` |
| LLM 的标准格式 | `build_system_prompt()` 逐字下发 |
| 入库校验基准 | `matches_template()` 从中解析章节定义 |

**判定口径只有一句：文档是否符合模板。** 合模板直接入库，不合交给 LLM 按同一份模板重写。
整套链路里**没有任何"修格式"的规则代码**——不剥围栏、不改标题层级。

为什么不用规则修格式：

- 格式问题的形态是**无限**的（AI 开场白、抄来的时间戳、奇怪包裹、乱标题层级……），
  用规则穷举必然不断追赶，改一次漏一类；
- 用规则去修还有个隐蔽危害：**把不合规文档"修成"看似合规的样子**，
  于是它绕过了本该进行的 LLM 整理（实测踩过：围栏尾随文字导致双重跳过）；
- "是否符合模板"则是一个有限的、可回答的问题。全部用**正向断言**描述标准文档长什么样：

  1. 首行即 `# 项目名`（任何前置内容都会让它失配 → 一条断言覆盖所有形态的前置噪音）
  2. 标题只有 `#` 与 `##` 两级
  3. 无代码围栏（简历文档不写代码）
  4. 必填章节齐全（当前为「一句话简介」「简历描述」）
  5. 模板章节出现顺序一致（允许插入自定义章节）

未见过的新形态只要破坏了任一断言就自然落到"不合规"，**不需要为它单独写规则**。

**必填 / 可选**：模板里行尾加 `<!-- optional -->` 即标记可选章节，由 `_SECTION_PATTERN` 解析。
增删章节、调整是否必填只需改那一个 md 文件，代码零改动。

**第 2 层的设计底线**：提示词硬约束「禁止编造 / 禁止夸大 / 禁止推断补全 / 禁止改数 / 禁止丢失」，
温度 0.2；任何失败一律回退原文。理由是简历用于求职，编造的量化数字或职责是实际损害而非"润色"。

> **部署注意**：模板是运行时资产。`.dockerignore` 原有 `*.md` 会把它排掉，
> 本地全绿但镜像内 `load_template()` 抛错导致上传全崩。已加取反规则，
> 并用 `test_doc_template.py::TestTemplatePackaged` 钉住。

流程改为**先预览后入库**：`preprocess` → 预览弹窗（可编辑、可对照原文）→ `confirm` 才落库。
避免系统在用户不知情的情况下改写其文档。

> 实测验证：给一份无任何数字的模糊原文，模型正确**省略**了「量化成果」章节而非编造数字；
> "做了一点前端页面"未被夸大成"负责前端开发"。约束生效。

#### 修正记录：三次迭代，一次比一次接近本质

| 版本 | 做法 | 为何不够 |
|---|---|---|
| v1 | 第 1 层用规则**修**格式（剥围栏、放宽标题层级），第 2 层仅"章节数 < 2"时触发 | 推荐系统样例：5 个 `###` 章节被判"已规范"跳过 LLM，但它缺「简历描述」，简历只能降级全文 |
| v2 | 给触发条件补一条"缺「简历描述」" | 仍是枚举条件；同时发现对话助手样例围栏剥离漏判（正则要求围栏闭合后直接到文件尾） |
| v3（现行） | 删掉全部"修格式"规则，改为**模板合规校验** | — |

v3 的关键转变：**规则不再修理格式，只回答"达标了吗"**。理由见 §8.5.1——

## 10. 风险与后续

| 风险 | 说明 | 处置 |
|---|---|---|
| `all_dbs` 全量加载 | `VectorRetriever` 构造时加载全部 FAISS，文档数增长后内存与启动时间线性上升 | 本期靠 `refresh` 增量规避重建；文档数 >500 时需改造为懒加载 + LRU（独立专项） |
| 进程内快照一致性 | 懒刷新依赖各进程自行比对版本，多进程下有秒级不一致窗口 | **当前不构成风险**：生产 `Dockerfile` CMD 固定 `--workers 1`（注释：Agent/TaskManager 是进程内单例），dev 编排 likewise 单进程。仅当改成多 worker 时才需 Redis pub/sub 广播 |
| embedding 成本 | 用户上传即触发向量化 | 靠 `max_docs_per_user` + 单文件大小上限约束 |
| 删除原子性 | 四处文件 + DB 行无法原子 | 失败留日志，`prune` 兜底 |

**为何不换 pgvector**（决策留档）：当前 58 个分块文档 / 17.1MB，FAISS 全内存暴力内积为
毫秒级；BM25 侧依赖 jieba 分词，PG 全文检索对中文支持弱，迁移后仍需保留 Python 侧 BM25，
会形成「向量在 PG、关键词在内存」的缝合架构。真正痛点（属性过滤、进程内快照）已由
「PG 映射表 + doc_ids 白名单 + 懒刷新」解决。触发重评的信号：分块文档数 >500、
FAISS 常驻内存 >300MB、或需多 worker 强一致。
