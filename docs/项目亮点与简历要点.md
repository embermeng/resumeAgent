# ResumeAgent 项目亮点与简历要点

> 用途：写简历时挑选亮点写进项目经历；面试时按"背景 → 问题 → 方案 → 结果"展开。
> 每个亮点都附：**一句话简历写法** + **可深挖的技术细节**（面试官追问时用）。

---

## 项目一句话介绍（简历用）

> 基于 LangGraph + FAISS + BM25 的 RAG 知识库与简历生成 Agent：支持课程 PDF 知识库问答、项目经历检索、按岗位要求生成/优化简历，配套 Streamlit Web UI，具备增量索引构建、混合检索、流式输出等工程化能力。

---

## 亮点一：知识库索引增量构建（成本优化）

### 背景与问题
知识库流水线（PDF 解析 → 分块 → BM25/向量索引）每次全量重建，28 个文档每次都要对全部分块调 Embedding API，新增 1 篇 PDF 也要付出全部文档的 API 成本与等待时间。

### 解决方案
- 以 `doc_id`（源文件哈希）为主键，打通文档级产物链：`parsed_pdfs/{doc_id}.json` → `course_chunks/{doc_id}.json` → `bm25_dbs/{doc_id}.pkl` + `vector_dbs/{doc_id}.faiss`
- 三级判断决定是否重建：**存在性检查**（产物缺失即建）→ **mtime 过期检测**（上游文件比下游新则重建）→ `--force` 强制全量
- BM25 索引原子写入（`.pkl.tmp` + `os.replace`），避免构建中断留下损坏索引
- `--prune` 清理孤儿索引（上游文档已删除的残留索引）
- 检索端按目录扫描、逐文档加载，新增索引零改动自动生效

### 结果（可量化）
- 新增 1 篇 PDF：从 ~28 次文档级 Embedding 调用降为 **1 次**，API 成本降至约 1/28
- 新增 12 个测试覆盖增量跳过 / 过期重建 / force / prune / 原子写入

### 面试追问预案
- **为什么用 mtime 而不是内容哈希？** —— 课程知识库文件量小、单机场景，mtime 判断 O(1) 且足够可靠；哈希要读全文件，收益不匹配成本（这是做过取舍的决策，不是没想到）
- **为什么是文档级增量而不是分块级？** —— 分块级增量需要维护 chunk→向量索引行的映射并支持局部更新/删除，FAISS 删除代价高；文档级粒度实现简单、正确性易保证，与课程文档"整篇新增/整篇更新"的使用模式匹配
- **如何防止半成品索引被检索到？** —— 临时文件 + 原子替换；检索端只认最终文件名

## 亮点二：知识问答失效的三重根因排查（最能体现工程能力）

### 背景与问题
网页问答答案与 PDF 内容不符、且被分到"闲聊"模式——表面上是"回答不准"，实际是**检索链路完全没生效**，LLM 在用自身知识硬答。

### 排查过程与三层根因（一条 bug 链）
1. **API 错误被静默吞掉**：`IntentClassifier` 未显式传模型，使用了当前 API Key 无权限的默认模型（返回 403）；而 `send_message` 不检查 `status_code`，错误响应被 `str()` 当作正常内容继续处理，恰好是合法 JSON 但缺字段 → 触发降级，且降级默认落到"闲聊"（不检索）。
   - 修复：API 非 200 立即抛异常；意图分类显式传配置模型；降级默认改为"快速回答"（保底走检索）
2. **BM25 中文分词失效**：索引和查询都用 `str.split()`，中文无空格，整句变成单个 token，检索完全无效。
   - 修复：封装统一分词器（jieba），**索引构建与查询侧强制共用同一套分词逻辑**（这是 BM25 中文检索的第一原则），并过滤零分结果避免"无匹配也返回内容"误导 LLM
3. **FAISS 中文路径静默失败**：faiss C++ 层 `fopen` 不支持中文路径，项目路径含中文导致 28 个向量索引全部加载失败且无报错。
   - 修复：读取侧先复制到临时文件再加载的兼容层（写入侧原有同样思路的 workaround）

### 结果
- 端到端复测原问题：意图识别正确 → 检索 top1 精确命中目标 PDF 的目标章节 → 回答完全基于检索内容并引用来源
- 测试数从 150 增至 156，全部通过

### 面试追问预案
- **怎么定位到这三层的？** —— 分层验证：先查意图分类输出（发现降级）→ 单独调用检索层（发现 BM25 返回无关内容、向量检索直接为空）→ 打日志到 faiss 加载（发现全部 `could not open`）→ 逐个修复并回归
- **最大的教训？** —— 三个问题都是"静默失败"：错误吞掉、分词失效、加载失败都不报错。修复之外还建立了原则：**外部 API 调用必须检查状态码；检索链路要有"空结果/零分"的显式语义**

## 亮点三：混合检索（BM25 + 向量）

### 背景与问题
单纯 BM25 在长查询下被高频词稀释排名；单纯向量检索对精确术语匹配不敏感。

### 解决方案
- `HybridRetriever`：BM25 与向量检索各自召回、加权合并（vector_weight=0.6），分数归一后融合排序
- 异常降级链：混合检索失败 → 纯 BM25 → 返回友好提示，保证问答功能不中断

### 面试追问预案
- 权重怎么定的？—— 中文课程语料上以语义匹配为主、术语精确匹配为辅，实测对比后取 0.6；可做成配置项
- 为什么不用 reranker 二次排序？—— 架构里已预留 reranker 模块，当前 top_n 规模下加权合并的性价比更高（说明有演进规划而非没考虑）

## 亮点四：PDF 解析从 Docling 迁移到 MinerU（GPU 加速）

### 背景与问题
Docling 解析中文课程 PDF 速度慢、对公式/表格还原一般。

### 解决方案
- 迁移到 MinerU（pipeline backend，`parse_method="auto"`），GPU 加速解析，输出干净 Markdown 并清理图片引用
- **对外接口保持不变**（`PDFParser` 类签名不动），上层 ingestion/CLI 零改动
- 测试同步重写（mock 新解析入口），新增图片清理、部分失败等用例；conftest 全局 mock 防止测试误触发真实模型加载
- 环境适配：解决 torch 在 RTX 5070 Ti 上需 cu130 索引、HF 模型缓存目录、子进程环境变量继承等问题

### 结果
接口零改动完成迁移，136 个测试全部通过，中文 PDF 在 GPU 上解析又快又准。

### 面试追问预案
- **为什么选 MinerU？** —— 针对中文文档优化、支持公式表格还原、开源可本地 GPU 部署，无 API 成本
- **迁移怎么保证不破坏上层？** —— 保持解析器抽象层接口稳定 + 测试先行的 mock 边界迁移

## 亮点五：流式输出（SSE 效果）优化

### 背景与问题
Web UI 必须等 Agent 完整生成后才一次性展示回答，长回答等待体验差。

### 解决方案（四层链路改造）
1. **API 层**：三个 provider 统一新增 `send_message_stream()` 生成器，DashScope 用 `stream=True, incremental_output=True` 拿增量块，流中错误块立即抛异常
2. **工具层**：`answer_question_stream()` 基于检索上下文流式问答
3. **Agent 层**：`run_stream()` yield 结构化事件流（`status` 阶段进度 / `token` 文本增量 / `done` 完整结果）
4. **UI 层**：Streamlit 占位符增量渲染，先展示"意图识别 → 检索 → 生成"阶段进度，首个 token 到达后逐字输出（带光标）

### 结果
- 用户从"等待完整响应"变为"秒见进度、逐字出答案"；实测增量块持续到达，首块延迟显著低于完整响应时间
- 新增 6 个流式相关测试，全量 162 个测试通过

### 面试追问预案
- **为什么不用真正的 SSE/WebSocket？** —— Streamlit 自带基于 WebSocket 的增量渲染机制（占位符 `st.empty()` 更新），在 Streamlit 框架内这就是标准的流式方案；若换自研前端，事件流结构（status/token/done）可直接映射为 SSE 事件
- **深思路径（简历生成）为什么没流式？** —— 简历是"草稿 → 按 JD 优化"两段式长文档生成，流式展示中间态会误导用户；改为输出阶段进度是权衡后的选择

## 亮点六：工程质量细节（穿插在以上亮点中，单独可提）

| 细节 | 说明 |
|---|---|
| tiktoken 特殊 token 兼容 | 课件 PDF 含 `<\|endoftext\|>` 字面量导致分块崩溃，用 `disallowed_special=()` 按普通文本编码，并加回归测试 |
| 降级策略设计 | 意图分类失败不再落到"闲聊"（不检索），而是落到"快速回答"，保证任何问题都经过知识库检索 |
| 原子写入 | BM25 索引 `.tmp + os.replace`；FAISS 沿用临时文件 + move（兼容中文路径） |
| 零分过滤 | BM25 无匹配时不返回 top 分块，避免无关内容误导 LLM 生成"知识库没有"的错误结论 |
| 测试覆盖 | 162 个测试全通过；关键修复（403 吞错、特殊 token、中文分词、中文路径）都有对应回归测试 |

## 简历写法示例（可直接摘抄/改写）

**项目名称**：ResumeAgent — 基于 LangGraph 的 RAG 知识库与简历生成 Agent

- 设计并实现文档级增量索引构建（存在性检查 + mtime 过期检测 + 原子写入 + 孤儿索引清理），新增文档的 Embedding API 成本降至全量重建的 1/28
- 排查并修复知识问答失效的三重根因：API 403 静默吞错导致意图降级、BM25 中文分词失效、FAISS 中文路径加载失败，修复后检索 top1 精确命中目标文档章节
- 实现 BM25 + 向量混合检索（加权融合 + 异常降级链），解决长查询高频词稀释与术语精确匹配的权衡
- 主导 PDF 解析从 Docling 迁移到 MinerU（GPU 加速），保持解析器接口零改动，解决 torch cu130 / 模型缓存等环境适配问题
- 为 Web UI 实现四层流式输出（API 生成器 → Agent 事件流 → 占位符增量渲染），回答从整块等待改为秒级进度提示 + 逐字输出

**技术栈**：Python / LangGraph / LangChain / FAISS / rank-bm25 / jieba / MinerU / DashScope / Streamlit / Pydantic / pytest

## 面试表达建议

1. **优先讲亮点二**：三重根因排查最能体现"发现问题 → 分层定位 → 系统修复"的工程能力，比单纯罗列功能有说服力
2. **每个亮点都用"背景 → 问题 → 方案 → 结果"四段式**，结果尽量带数字（成本 1/28、162 测试、28 个文档）
3. **主动暴露权衡**：文档级 vs 分块级、mtime vs 哈希、流式 vs 非流式的取舍理由，展示的是设计能力而非实现能力
4. **教训类回答要落到原则**：如"外部调用必须检查状态码""索引与查询必须共用分词器"，把个案抽象成可复用规则
