- 推荐练法：遮住答案讲 60～90 秒，再逐项检查题干是否都答到了；每天选一个模块，最后用第 117～120 题把知识串成项目故事。

## 1. Python 与 FastAPI

### Q001【P0】Python 的 GIL 是什么？多线程是不是没有用？

**参考答案：**
- **是什么：** GIL 全称 Global Interpreter Lock，中文叫“全局解释器锁”，是常规 CPython 解释器内部的一把互斥锁。同一解释器中的线程执行 Python 字节码前必须持有它，因此同一时刻通常只有一个线程执行 Python 字节码。它是解释器实现机制，不是 Python 语言规定所有实现必须有的锁。
- **为什么存在：** CPython 需要维护对象引用计数等共享内部状态。GIL 让这些内部操作更容易保持安全，也简化了早期解释器和 C 扩展的实现；代价是限制多线程执行 Python 字节码的并行度。
- **怎么运行：** 线程会按解释器调度切换 GIL；阻塞 I/O 和某些 C 扩展计算也会释放它。其他线程可在这段时间运行，所以 GIL 不会把整个程序的所有活动都锁死。
- **多线程仍然有用：** 多个同步网络请求或文件操作可重叠等待时间；释放 GIL 的原生计算也可能并行。但两个线程同时做大量纯 Python 计算，在同一常规解释器中通常只能交替执行，不能直接获得双核加速。
- **怎么选：** 异步库支持良好的 I/O 用 asyncio，同步 I/O 可用线程；纯 Python CPU 密集任务考虑多进程、独立 worker 或原生计算库，并衡量序列化与内存成本。

**易错点：** GIL 保护解释器内部状态，不保证“查余额再扣款”等多步业务操作原子化；共享业务状态仍可能需要锁。较新的 CPython 有可选 free-threaded 构建，不能说“Python 所有版本永远都有 GIL”；本项目按常规启用 GIL 的环境讨论。

### Q002【P0】迭代器、生成器和普通函数有什么区别？为什么流式接口用生成器？

**参考答案：**
- **迭代器**是实现迭代协议的对象：`iter(it)` 返回它自身，`next(it)` 调用 `__next__()` 取得下一项，没有下一项时抛出 `StopIteration`。列表是可迭代对象，但列表本身不是迭代器，需要先 `iter(列表)`。
- **生成器**是一种由 Python 自动维护执行状态的迭代器。调用含 `yield` 的生成器函数先得到生成器对象；迭代时才执行函数体，遇到 yield 产出一项并暂停，下次从暂停处继续，局部变量也保留。
- **普通同步函数**调用后执行到 return 或结束，再一次性返回结果；生成器则按需逐项产出。生成器也是迭代器，但自定义迭代器不一定是生成器。
- 流式接口不必等完整回答生成后再发送，也不必先攒好全部数据：生成一段就 yield 一段，可减少首段等待和一次性内存占用。
- SSE 可以把业务事件逐个转成帧交给响应层，但生成器不自动等于异步：同步生成器里照样可能存在阻塞调用。
- 生成器关闭时应在 `finally` 释放资源；处理 `GeneratorExit` 时不能继续 `yield` 业务数据。

**项目关联：** 对话端点把 Agent 的事件生成器包装成 SSE；断线后的终态补写进 Redis，而不是向已关闭连接继续发帧。

### Q003【P0】可变默认参数、浅拷贝和深拷贝会带来什么问题？

**参考答案：**
- 函数默认参数在定义时求值。`def f(items=[])` 会让多次调用共用同一个列表，可能造成跨请求数据污染；应使用 `None`，在函数内新建。
- 浅拷贝只复制最外层，嵌套列表或字典仍共享引用；深拷贝递归复制，但成本更高，也不适合数据库连接、锁、网络客户端等资源对象。
- Web 服务应明确哪些对象是只读共享配置，哪些是请求私有状态。数据库 Session、当前用户、当前对话缓冲不能随意放进全局可变单例。

**追问：** 时间字段默认值应传可调用对象，而不是在模块导入时先算出一个固定时间；可变 ORM 默认值也应使用工厂函数。

### Q004【P0】FastAPI 路由什么时候写 `async def`，什么时候写 `def`？

**参考答案：**
- `async def` 适合调用异步数据库、异步 HTTP 等可等待操作；等待期间事件循环可服务其他请求。
- 普通 `def` 路由通常由框架放在线程池运行，适合同步阻塞库。同步生成器作为流式响应内容时也会通过线程池迭代。
- 在 `async def` 内直接调用 `time.sleep()`、同步 `requests` 或重 CPU 计算，仍会阻塞事件循环。可替换为异步库、显式线程卸载，或移到进程/任务队列。
- 框架不会自动把异步路由中调用的每个普通函数都放进线程池；线程池也有容量上限。

**项目关联：** 对话流目前使用同步路由和同步生成器；多个数据库读接口使用 `AsyncSession`。选择依据是依赖库和阻塞边界，不是“async 看起来更高级”。

### Q005【P0】FastAPI 的 `Depends` 解决什么问题？依赖的生命周期怎么管理？

**参考答案：**
- `Depends` 是 FastAPI 声明依赖注入的方式：路由声明需要什么，框架先调用依赖函数，再把返回值注入路由参数；依赖还可以声明自己的子依赖。
- 它把重复的认证、Session 创建等逻辑从各路由中抽出，使路由专注业务，也能在测试中用 `dependency_overrides` 替换真实依赖。
- 带 `yield` 的依赖把生命周期分成“准备资源 → yield 提供资源 → 退出时清理”；Session 适合在每请求的上下文中创建，用 finally / 上下文管理器保证异常时也关闭，失败事务应回滚。
- 同一个请求中依赖结果通常会按框架规则缓存复用，这不等于跨请求单例。
- 依赖清理与流式响应的时机受 FastAPI 版本和依赖 scope 影响，长流不应无理由占着数据库事务或连接。

**易错点：** 不能把请求的 Session 直接传给响应结束后才运行的任务；任务应自己创建会话。

### Q006【P0】Pydantic、ORM 模型和 TypeScript 类型分别负责什么？

**参考答案：**
- **Pydantic** 是 Python 数据校验库，把输入解析成声明的类型并检查约束，在程序运行时工作；FastAPI 用它描述和校验请求、响应数据。
- **ORM（Object-Relational Mapping，对象关系映射）模型**把 Python 类及属性映射到数据库表和列，描述存储结构与对象关系；它不应该直接充当对外接口的数据合同。
- **TypeScript 类型**主要在编译期检查前端代码，编译成 JavaScript 后类型通常被擦除，不能代替服务端对实际请求的校验。
- 例如注册时，TS 帮助前端正确使用字段，Pydantic 校验邮箱格式和密码长度，业务层处理注册策略，数据库唯一约束兜住并发注册同一邮箱。
- 响应模型限制对外字段，避免直接暴露密码哈希、内部路径等；数据库允许 `NULL` 的字段，响应模型也应按业务正确处理。
- `as SomeType` 不会运行时验证服务端 JSON；关键流事件应有必要的结构检查。

**易错点：** 数据库能查出记录，不代表响应模型一定能序列化；一条不符合必填字段或 Literal 限定的记录，可能使整个列表响应失败。

### Q007【P0】REST 接口怎样选择方法和状态码？什么叫幂等？

**参考答案：**
- GET 查询；POST 创建资源或提交动作；PUT 通常完整替换；PATCH 部分更新；DELETE 删除。DELETE 的目标状态应幂等，即重复执行不产生额外业务副作用，不要求每次状态码相同。
- 常见状态码：200 成功、201 已创建、202 已受理但未完成、204 成功且无响应体；400 请求错误、401 未认证、403 无权限、404 不存在、409 状态冲突、422 校验失败、429 限流。
- 幂等是“重复请求的预期业务效果与一次相同”，不是“每次响应体相同”。POST 可以通过业务幂等键实现幂等。
- 后台任务返回任务标识和状态查询入口，HTTP 受理成功不等于解析已经成功。

**追问：** 自动重试 POST 前必须判断副作用；不能把“网络断了”直接等同于“服务器没执行”。

### Q008【P0】文件上传接口需要做哪些安全与资源保护？

**参考答案：**
- 校验认证、对象归属、文件大小、允许的格式及实际解析结果；不能只信扩展名和客户端 MIME。
- 使用服务端生成的存储名，限制落盘目录，防止路径穿越、同名覆盖；不要把任意客户端路径交给 worker 读取。
- 同时限制代理层和应用层大小、解析并发、执行时间及临时文件生命周期；压缩格式还需防止解压体积异常。
- 返回业务 ID，不直接泄露服务器文件路径；日志和模型请求中谨慎处理简历里的个人信息。

**项目关联：** 任务消息传服务端落盘路径，API 与 worker 需要共享存储；“传的是路径”不代表可以接受用户指定任意路径。

## 2. PostgreSQL、SQL 与事务

### Q009【P0】B-tree 索引为什么能加速查询？索引有什么代价？

**参考答案：**
- **索引**是数据库为加速定位记录而额外维护的数据结构；B-tree 是平衡的多路搜索树，键按顺序组织，一个内部节点可以指向多个子节点。PostgreSQL 将这种索引访问方法称为 B-tree，其叶层存放索引条目。
- 查找时从根节点比较键值，逐层缩小范围，不必检查每一行；节点通常容纳多个键，分支多、树高低，因此需要访问的数据页较少。有序叶层也利于范围扫描和符合条件的排序。
- PostgreSQL 的 B-tree 索引通常存键和指向堆表元组的位置，找到索引项后往往还需访问堆表取得数据 / 检查可见性；满足覆盖和可见性条件时可使用 Index Only Scan。它不等同于 InnoDB 的聚簇主键结构。
- 索引占磁盘和缓存，INSERT、DELETE、部分 UPDATE 需要维护它；索引越多，写入和维护成本可能越高。
- 是否使用索引由优化器按成本决定。小表或命中大部分行时，顺序扫描可能更快。

**易错点：** 不要把 MySQL 的“主键索引叶子就是整行数据”“二级索引一定按主键回表”原样套到 PostgreSQL。

### Q010【P0】哪些情况会让索引没有发挥作用？

**参考答案：**
- 对索引列做函数或不匹配的类型转换，例如只有普通 `email` 索引却查 `lower(email)`；可按查询需要建表达式索引或统一规范化存储。
- 普通 B-tree 很难高效处理前置通配的 `LIKE '%关键词%'`；前缀匹配也受排序规则、操作符类等影响，不能一概而论。
- 联合索引与过滤、排序条件不匹配，返回行数太多，或统计信息不准，优化器可能选择其他路径。
- `OR`、`!=`、`IS NULL` 并非天然“索引失效”；PostgreSQL 可用 Bitmap Scan、多个索引或索引中的 NULL 条目。

**口述重点：** “我先看执行计划，而不是背一张绝对失效清单。”

### Q011【P0】联合索引的列顺序怎么设计？什么叫最左前缀？

**参考答案：**
- **联合索引**是在多个列上建立的一个索引。例如 `(a, b, c)` 先按 a 排，相同 a 内按 b 排，再按 c 排，不是分别建立三个独立索引。
- **最左前缀**指从索引第一列起连续的一段键，如 `(a)`、`(a,b)`、`(a,b,c)`。这些前导列的等值约束通常能有效缩小扫描区间；只查 b 时，因为 b 分散在不同 a 分组中，通常不具备同样的定位效率。
- 设计时先看高频查询，把经常一起出现的等值条件、范围条件、排序和 LIMIT 综合考虑；WHERE 中条件的书写顺序本身不决定索引是否可用。
- 对“查询某个会话的消息并按时间翻页”，可考虑 `(conversation_id, created_at, id)`：先定位会话，再按时间及主键读取，`id` 用于同时间下稳定排序。
- 范围条件之后的列不等于“完全不能使用”，但未必能同样有效地缩小扫描范围或满足排序。
- 缺少最左列也不代表所有数据库版本、所有场景绝对不能用索引，最终要看版本能力和执行计划。

**追问：** 高区分度列并非永远放第一，应优先看真实查询的等值条件、范围、排序、LIMIT 和复用情况。

### Q012【P0】拿到一条慢 SQL，你怎么定位？

**参考答案：**
1. 确认慢的是数据库执行、等待锁、获取连接，还是网络和 ORM 组装；记录参数、频次和数据规模。
2. `EXPLAIN` 展示优化器计划怎样扫描、连接和排序数据；在安全环境用 `EXPLAIN (ANALYZE, BUFFERS)` 实际执行，比较预估与真实行数、节点耗时和缓冲读取。`cost` 不是毫秒，`actual time` 才是实际时间信息，多次循环的节点还需结合 loops 阅读。
3. 关注估计行数偏差、循环次数很大的 Nested Loop（对外层每行重复查询内层）、读了大量行却只返回少量行、排序落盘和锁等待。
4. 再考虑改查询、索引、统计信息或分页方式；改完用同一数据和参数复测，同时观察写入成本。

**易错点：** `ANALYZE` 会真实执行语句。不要在生产随手分析写语句，也不要只看到 `Seq Scan` 就判定有问题。

### Q013【P0】为什么深分页变慢？游标分页怎么写？

**参考答案：**
- `OFFSET` 很大时，数据库通常仍需访问并跳过前面的匹配记录；并发插入还可能导致页间重复或遗漏。
- 游标分页记住上一页最后一条排序键，结合联合索引直接继续查询；排序必须稳定，时间相同要用主键打破平局。

```sql
SELECT id, content, created_at
FROM messages
WHERE conversation_id = :conversation_id
  AND (created_at, id) > (:last_created_at, :last_id)
ORDER BY created_at, id
LIMIT :page_size;
```

**怎么翻页：** 第一页不带游标比较条件；后续用上一页最后一条的 created_at / id 继续。若改成倒序，就同时使用 `<` 和 `ORDER BY created_at DESC, id DESC`，比较方向与排序方向必须一致。

**边界：** 这是 SQL 参数示意，不是项目已提供的接口；游标分页不擅长直接跳任意页，动态数据下也不自动形成跨请求快照。

### Q014【P0】SQL 的 NULL、COUNT 和 JOIN 最容易错在哪里？

**参考答案：**
- NULL 表示未知或缺失，比较要用 `IS NULL`，不能用 `= NULL`；WHERE 只保留结果为 TRUE 的行。
- `COUNT(*)` 统计行，`COUNT(column)` 忽略该列的 NULL，`COUNT(DISTINCT column)` 还会去重并忽略 NULL。
- `LEFT JOIN` 后在 WHERE 对右表列做普通过滤，可能把没有匹配的行过滤掉，效果接近 INNER JOIN；需保留左表行时应考虑把条件放入 ON。
- `NOT IN` 的子查询若含 NULL 可能产生意外结果，反连接场景常用 `NOT EXISTS` 表达得更清楚。

**项目关联：** 任务归属允许 NULL 时，要明确它表示什么；不能直接把 NULL 当成“公共可访问”。

### Q015【P1】如何查询每个会话的最新一条消息？

**参考答案：** 可用窗口函数按会话分组，再按时间和主键降序编号，取第一条。

```sql
SELECT id, conversation_id, content, created_at
FROM (
    SELECT id, conversation_id, content, created_at,
           ROW_NUMBER() OVER (
               PARTITION BY conversation_id
               ORDER BY created_at DESC, id DESC
           ) AS rn
    FROM messages
) AS ranked
WHERE rn = 1;
```

**追问：** PostgreSQL 还可以用 `DISTINCT ON`。不能把 `MAX(created_at)` 与未分组的任意 `content` 混在一起，就认为内容一定属于最新记录；实际接口还需加用户权限过滤。

### Q016【P0】事务的 ACID 分别是什么？有事务就不会出现业务错误吗？

**参考答案：**
- **事务**是被当作一个整体提交或回滚的一组数据库操作，例如转账中的扣款和入账；ACID 是描述事务保证的四个属性。
- **Atomicity，原子性：** 整组修改一起提交或一起回滚，避免扣款成功而入账失败只留下半笔转账。
- **Consistency，一致性：** 在数据库约束和正确业务逻辑下，从一个合法状态变到另一个合法状态，例如转账前后总额保持不变；它不是“所有副本随时看到相同数据”的同一概念。
- **Isolation，隔离性：** 规定并发事务能看到彼此哪些中间结果，以及可能发生哪些竞争，具体保证取决于隔离级别。
- **Durability，持久性：** 提交成功的数据按数据库日志与持久化配置保存，正常恢复后不会因应用进程退出就消失；可靠性仍受刷盘、存储和故障模型影响。
- **有事务仍会出业务错误：** 数据库不会自动理解“余额不能透支”“一个 refresh token 只能用一次”等所有业务语义，需要约束、条件更新或锁配合。
- 一个 PostgreSQL 事务不能自动覆盖 Redis 发布、外部模型调用和文件写入；跨系统需要补偿、幂等或 outbox 等设计。

### Q017【P0】脏读、不可重复读、幻读是什么？PostgreSQL 的隔离级别有什么特点？

**参考答案：**
- **脏读：** 读到其他事务未提交、以后可能回滚的数据。**不可重复读：** 同一事务重复读同一行，因其他事务提交修改而看到不同的值。**幻读：** 重复执行相同条件查询，因其他事务提交而看到不同的匹配行集合。
- **Read Committed（读已提交）**是 PostgreSQL 默认级别，普通查询通常每条语句获得新快照，不读未提交数据，但两次查询可以看到其他事务刚提交的新值或新行。
- **Read Uncommitted（读未提交）**在 SQL 标准中允许脏读，但 PostgreSQL 实际把它按 Read Committed 处理，并不会开放脏读。
- **Repeatable Read（可重复读）**提供事务级稳定快照，在 PostgreSQL 中也能防止通常意义上的幻读；快照通常在第一条非事务控制语句时建立，而非 BEGIN 时，事务仍能看到自己的修改。
- Repeatable Read 仍可能出现**写偏斜**：例如两名值班者各自看到另一人还在岗，各修改自己的记录为离岗，最终无人值班。虽然改的是不同行，却破坏了跨行业务约束，结果不等价于某个串行执行顺序。
- **Serializable（可串行化）**要求成功提交的并发事务效果等价于某个逐个执行的顺序。PostgreSQL 会检测可能破坏这一保证的依赖冲突，必要时中止事务；应用需重试整个事务，而不是认为该级别自动把所有请求排成一条队列。

**易错点：** 不要把 SQL 标准中“可重复读允许幻读”的表格当成 PostgreSQL 实际行为的完整描述。

### Q018【P0】MVCC 如何减少读写互相阻塞？为什么需要 VACUUM？

**参考答案：**
- **MVCC（Multi-Version Concurrency Control，多版本并发控制）**为同一逻辑记录保留不同版本，并让事务按照快照选择自己可见的版本。快照可理解为“本次读取应看见哪些已提交事务”的视图，而不是复制一份整库。
- PostgreSQL 更新通常生成新元组版本，旧版本暂时保留；事务 ID 与快照共同参与可见性判断。写者还没提交时，普通读取可继续看符合快照的旧版本，因此不必等待该写者完成。
- 写操作之间仍会冲突，`SELECT FOR UPDATE` 等锁定读取也会等待；MVCC 不是“数据库没有锁”。
- **VACUUM 是清理和维护机制：** 已不再被任何相关快照需要的旧版本应被回收，否则表和索引不断膨胀；它还维护可见性信息，并通过冻结等机制降低事务 ID 回卷风险。普通 VACUUM 通常把空间留给表内复用，不会立即把文件缩小还给操作系统。
- autovacuum 会自动触发维护，但长事务 / 长期快照会让某些旧版本仍必须保留，妨碍清理；因此要监测长事务，不能只调高清理频率。

**项目关联：** 不应为了等待几十秒的模型输出一直保持数据库事务打开。

### Q019【P0】乐观锁、悲观锁和死锁分别怎么理解？

**参考答案：**
- 悲观锁先锁再修改，例如事务内 `SELECT ... FOR UPDATE`，适合必须保护读后写的一小段操作；锁应持有得短。
- 乐观锁通过版本号或旧状态作为 UPDATE 条件，检查影响行数发现冲突；适合冲突较少的业务。
- 死锁是多个事务形成循环等待。统一访问资源顺序、缩短事务、使用合适索引能降低风险。
- 数据库发现死锁通常会中止其中一个事务；业务应对可重试错误做有上限的整事务重试，而非只重发最后一条 SQL。

**易错点：** 在行锁期间调用 LLM、等待用户或下载 PDF，会把外部慢请求变成数据库阻塞。

### Q020【P0】“先查再改”为什么可能有并发问题？如何原子扣减或迁移状态？

**参考答案：** 两个请求可能同时读到库存为 1，都认为可以扣减，再各自写回 0，造成发出两件商品却只记录一次扣减。应把判断和修改放到同一条条件 UPDATE，并检查返回行或影响行数。

**原子扣减示例：** 下例 products / stock 是教学用表和字段，不是本项目现有表；quantity 必须校验为正数。

```sql
UPDATE products
SET stock = stock - :quantity
WHERE id = :product_id AND stock >= :quantity
RETURNING stock;
```

**状态迁移示例：** 只有仍为 pending 的任务才允许被当前调用改为 running。

```sql
UPDATE build_tasks
SET status = 'running'
WHERE task_id = :task_id AND status = 'pending'
RETURNING id;
```

**机制：** 数据库用行级并发控制保护更新；在 PostgreSQL Read Committed 下，竞争者等待前一更新完成后，会按更新后的行重新检查相关条件。更高隔离级别也可能返回需重试的并发错误，不能忽略执行结果。

**边界：**
- 返回记录表示这个调用成功抢占了状态转换，没返回需区分已执行、状态不符或资源不存在。
- 这只能保护该数据库状态转换，不能独自保证外部解析调用“恰好一次”。
- 是否需要先 SELECT，取决于是否必须读取旧值和执行复杂业务判断，不取决于新值来自哪里。

### Q021【P0】为什么有了应用层校验，还需要唯一约束、外键和 NOT NULL？

**参考答案：**
- 两个请求可能同时通过“邮箱不存在”的查询，只有数据库唯一约束能在最终写入时可靠兜底；应用捕获冲突并返回友好错误。
- 外键防止引用不存在的父记录，NOT NULL 保证必要字段存在，CHECK 可限制单行合法取值。
- 大小写不敏感的邮箱唯一性，需要规范化写入并配套约束，或使用合适的表达式索引 / 类型方案；普通区分大小写唯一约束不自动解决它。
- PostgreSQL 普通 UNIQUE 默认允许多个 NULL；“公共素材”和“用户私有素材”有不同唯一性规则时，可使用部分唯一索引。

### Q022【P1】数据库连接池如何配置？为什么应用扩容后数据库反而崩了？

**参考答案：**
- **连接池**维护可复用的数据库连接：请求按需借用，用完归还，而不是每次查询都重新握手；池本身也限制应用同时占用多少连接。
- 以 SQLAlchemy 常用池为例，`pool_size` 控制池可保留的连接数，`max_overflow` 控制额外临时连接，`pool_timeout` 控制等待可用连接的上限。失效连接可评估 `pool_pre_ping` / `pool_recycle`，但它们不能自动重放失败事务。
- 先从数据库可承受连接数中预留管理、迁移等容量，再给全部 API 和 worker 分配预算。例：4 个 API 进程各配置 size=5、overflow=5，API 理论连接上限就是 40，还未计入 worker；这不是必然常驻 40 个连接，也不是推荐固定参数。
- 扩容副本会同时增加独立连接池和数据库请求量，超过连接或计算容量后，锁竞争、排队和超时可能一起上升；应用机器多不代表数据库能力同步增加。
- 长事务、连接未释放或慢查询会长期占池。先观测池等待、活跃连接、事务时长和数据库资源，通过压测调整池与并发；不要把池等待一律当成需要继续加连接。

## 3. SQLAlchemy 与 Alembic

### Q023【P0】SQLAlchemy 的 Engine、Connection、Session 有什么区别？

**参考答案：**
- **Engine** 是数据库访问入口，配置数据库方言、驱动和连接池，适合按进程长期复用；它本身不是一条始终占用的连接。
- **Connection** 是从 Engine 获取的数据库连接操作上下文，可执行 SQL 并管理该连接上的事务，关闭时通常把底层连接归还池。
- **Session** 是 ORM 工作单元，管理对象的新增 / 修改 / 删除、事务以及 identity map。identity map 让同一 Session 中同一主键通常对应同一 Python 对象；它不是全局查询结果缓存。
- 三者关系是：Session 绑定 Engine，执行数据库操作时按需获取 Connection。应用通常复用 Engine，但为每个请求或独立后台任务新建 Session，结束时提交或回滚并关闭。
- Session 不适合跨线程共享，AsyncSession 不适合被多个并发任务共享；同进程并发协程也应各有自己的事务上下文。

**项目关联：** Web 异步读接口与同步 worker 可以分别使用异步和同步会话工厂，而不是把 AsyncSession 强行桥接进同步任务。

### Q024【P0】`add`、`flush`、`commit`、`refresh`、`rollback` 分别做什么？

**参考答案：**
- `add` 把对象纳入 Session；`flush` 把待执行变更发送到数据库事务中，常可获得生成的主键，但没有提交事务。
- `commit` 通常会先 flush 再提交；`refresh` 从数据库重新读取对象字段，不是持久化操作。
- `rollback` 回滚当前事务；flush 或 commit 失败后，通常需要 rollback 才能继续使用这个 Session。
- `expire_on_commit=False` 可以避免提交后属性被自动过期，但不会把对象变成永远新鲜，也不能代替显式刷新或正确的并发控制。

**易错点：** “拿到了自增 ID”不等于“另一连接已经能查询到记录”。

### Q025【P0】什么是 N+1 查询？`joinedload` 和 `selectinload` 怎么选？

**参考答案：**
- 先查 N 个父对象，再逐个访问懒加载子关系触发 N 次 SQL，形成 1+N 次查询；接口返回看似正常，延迟随数据量增长。
- `selectinload` 常通过父主键集合分批查子表，适合集合关系，避免 JOIN 造成大量父行重复。
- `joinedload` 在同一查询中 JOIN 加载，适合部分标量关系或较小结果，但集合关系可能放大行数，SQLAlchemy 某些用法还要求 `unique()` 去重。
- 选择取决于结果基数和分页场景；用 SQL 日志和查询次数测试验证，不要把所有关系一律 eager load。

### Q026【P0】为什么异步 ORM 中访问一个属性也可能报错？

**参考答案：**
- 属性可能是尚未加载的关系，或提交后被标记过期；访问时 ORM 想隐式发 SQL，但普通属性访问没有合适的 await 上下文。
- 常见策略是在查询时显式预加载、按需 `refresh`，或使用框架支持的 awaitable 属性，避免序列化响应时偷偷触发 I/O。
- `expire_on_commit=False` 只解决提交后过期的一类情况，不解决所有懒加载问题。
- Session 关闭后访问未加载字段还可能遇到 detached 对象错误；DTO 转换应在数据齐全时完成。

### Q027【P0】SQLAlchemy 查询里为什么不能用 Python 的 `and`？异步链式查询怎么写？

**参考答案：** Python `and` 会先进行 Python 布尔求值或短路，不能用来可靠构造 SQL 多条件表达式；应使用多个 `where` 参数、`and_()`，或带括号的 `&`。

```python
stmt = select(Message).where(
    Message.conversation_id == conversation_id,
    Message.role == "assistant",
)
result = await session.execute(stmt)
messages = result.scalars().all()
```

**追问：** `await session.execute(stmt).scalars()` 的调用优先级不符合预期；应先 await 获得结果，再取 scalars，或显式加括号。上例假设已导入模型和 `select`。

### Q028【P0】ORM 的 cascade 和数据库的 `ON DELETE` 是一回事吗？

**参考答案：**
- **不是。** ORM cascade 是对象关系层的“连带操作规则”，由 SQLAlchemy 在处理对象时执行；数据库 `ON DELETE` 是外键上的“删除父行后如何处理子行”规则，由数据库执行，直接 SQL 删除也受其约束。
- ORM cascade 不只涉及删除：`save-update` 可把关联对象纳入 Session，`delete` 可随父对象删除子对象，`delete-orphan` 可在子对象脱离所属关系时删除它；是否启用必须明确配置。
- 只配 ORM cascade，不代表所有批量 DELETE 或外部 SQL 都会自动清理子表；反过来也要让 ORM 配置与数据库策略保持一致。
- `ON DELETE SET NULL` 把子行外键置空，所以列必须可空；`CASCADE` 删除相应子行；`RESTRICT` / NO ACTION 等策略可在不满足约束时阻止父行删除，但检查时机可能不同。
- 选择由业务语义决定：消息可随会话删除，任务历史可能希望保留并清空用户归属。

**易错点：** SQLite 测试中的外键执行规则和生产 PostgreSQL 不同，测试通过不能直接证明删除链路安全。

### Q029【P0】Alembic 解决什么问题？`autogenerate` 能全自动迁移吗？

**参考答案：**
- Alembic 用版本化脚本管理 schema 演进，记录数据库处于哪个 revision，避免各环境靠手工改表漂移。
- 常见流程：修改模型 → 生成候选迁移 → 人工检查 → 在测试库验证 → 执行 `upgrade` → 验证应用兼容性。
- `autogenerate` 是候选差异，不保证理解重命名、数据回填、业务语义和所有约束；把改名误判成删列再加列会丢数据。
- 已在共享环境执行的迁移通常新增后续 revision 修正，而不是静默改历史脚本；`create_all()` 不是生产迁移方案。

### Q030【P1】有存量数据时，如何新增一个必填外键列而不影响服务？

**参考答案：**
1. 采用“先扩展、后收紧”：先新增可空列，让旧应用仍能运行，再部署兼容新旧数据、且为新写入填写该列的应用。
2. 按业务归属找到真实存在的父记录，分批回填旧行；持续写入期间要防止旧版本应用继续产生空值，并检查孤儿数据。
3. 验证回填完整性后再建立 / 验证外键，确认不再有空值后收紧 NOT NULL，最后移除过渡逻辑。
4. 评估每个 DDL 的锁和扫描成本；PostgreSQL 外键可考虑先 `NOT VALID` 再单独验证，大索引可评估并发创建，但要遵守各自事务限制。
5. 用接近生产的数据量演练并设置锁等待策略，必要时安排维护窗口。这是在降低中断风险，不是承诺任意表上所有 DDL 都完全无锁、零影响。

**易错点：** 给外键列随便设 `DEFAULT 0` 并不能创造一个合法父记录；应用回滚也不代表数据库结构可以无损降级。

## 4. Redis 与缓存

### Q031【P0】为什么用了 PostgreSQL 还要 Redis？Redis 在项目中有几种角色？

**参考答案：**
- PostgreSQL 是关系数据库，擅长事务、约束和关系查询；Redis 是以内存访问为主、支持多种数据结构的键值存储，适合低延迟访问的缓存和短期状态。
- PostgreSQL 负责用户、会话、消息和任务等业务权威数据；Redis 缓存重复检索结果，可减少重复计算和外部调用。它们是分工互补，不是加 Redis 后就不需要数据库。
- ResumeAgent 中可按四项职责理解 Redis：检索结果缓存、Celery broker（排队和投递任务）、Celery result backend（记录执行结果 / 状态）、SSE 已生成事件的重放缓冲。
- 缓存可失效后重建；任务队列丢失可能导致任务不再执行；重放缓冲丢失会影响断线恢复，这些角色的可靠性要求不同。
- 同用 Redis 不代表应该永久共用一个实例。规模增长后可按可靠性和淘汰策略隔离；仅分 logical DB 不隔离内存、故障和实例级淘汰策略。

### Q032【P1】Redis 为什么快？“Redis 是单线程”准确吗？

**参考答案：**
- 主要原因是内存访问、高效数据结构和事件驱动网络模型；许多命令在主执行线程顺序处理，减少了锁竞争。
- 不能说 Redis 整个进程只有一个线程：不同版本支持 I/O 线程，持久化等也有后台工作。
- 单条命令的原子执行不等于“GET 后 SET”两条命令整体原子；组合操作可考虑 Lua、事务配合 WATCH 或专用原子命令。
- 大 key、大范围扫描、长 Lua 脚本仍会阻塞服务；pipeline 主要减少往返开销，不提供整个批次的业务事务保证。

### Q033【P0】String、Hash、List、Set、ZSet、Stream 分别适合什么？

**参考答案：**
- **String：** 一个 key 对应一个字符串 / 字节值，适合 JSON 缓存、token 或计数器；数字值可通过 INCR 原子递增。
- **Hash：** 一个 key 下保存多组 field-value，适合需要按字段读写的用户资料或任务摘要，避免每次重写整个 JSON。
- **List：** 有顺序、允许重复的元素序列，可从两端操作，适合最近消息列表和简单队列；仅靠弹出元素不具备完整可靠消费确认机制。
- **Set：** 无序且元素唯一，适合去重、成员判断、共同标签等集合运算。
- **ZSet（Sorted Set）：** 元素唯一且关联分数，适合排行榜、按时间分数排序的候选任务等；用它表示延迟任务时，消费者仍需实现抢占与确认。
- **Stream：** 带消息 ID 的追加式记录结构，可回溯读取，并支持消费组和已投递未确认消息的 pending 管理，适合需要消费者协作与确认的事件处理。
- **与 Pub/Sub 区分：** Pub/Sub 只向在线订阅者分发，离线期间消息通常不保留，不能单靠它实现可靠重放。类型选择要看访问方式和可靠性需求，不是所有“事件流”都必须用 Stream。

**项目关联：** 当前 chat 重放使用 Redis 列表记录事件，不应在面试里说已经实现了 Redis Stream 消费组。

### Q034【P0】什么是旁路缓存（Cache Aside）？读写顺序怎样安排？

**参考答案：**
- **是什么：** Cache Aside 是由应用自行协调缓存与权威数据源的模式。缓存放在数据源“旁边”，数据库不会因为记录变化就自动替应用同步这份缓存；缓存缺失时仍能回源得到数据。
- **读：** 先查缓存，命中直接返回；未命中查数据库或执行检索，把结果写入缓存并设置 TTL（Time To Live，有效存活时间），再返回结果。
- **写：** 常见做法是先成功提交权威数据源的更新，再删除相关缓存，让后续读取回填新值；更新失败时不能先把缓存当成已写成功。
- 删除通常比直接更新缓存更简单，避免多请求用不同旧值写回；但读写竞争仍可能造成短时间脏缓存。
- 缓存只是加速层，不应成为隐式唯一数据源；需要明确失效机制、可接受的陈旧时间和降级压力。

**项目关联：** 检索缓存未命中时回源到检索计算，不是简单查一张数据库表。

### Q035【P0】缓存穿透、击穿、雪崩怎么区分？分别怎么解决？

**参考答案：**
- **穿透：** 不存在的数据反复回源。输入校验、短 TTL 空结果缓存，必要时布隆过滤器；布隆过滤器有假阳性，不能代替最终查询。
- **击穿：** 单个热点 key 过期，大量请求同时重建。按 key 合并请求、互斥回源，或逻辑过期后异步刷新。
- **雪崩：** 大批 key 同时失效或 Redis 整体故障，引发集体回源。TTL 加随机抖动，配合限流、熔断、容量保护和高可用。
- 随机 TTL 主要缓解集体到期，不能解决单个热点重建，也不能解决 Redis 整体宕机。

**项目关联：** 当前有空结果短 TTL 和正常结果 TTL 抖动；不要据此宣称已实现了分布式互斥回源。

### Q036【P0】检索缓存 key 应包含哪些内容？为什么不能只用问题文本？

**参考答案：**
- key 必须覆盖所有影响结果的参数：规范化 query、类别、top-k、融合权重、可见文档集合，以及需要时的知识库 / 模型版本。
- 多租户场景需包含租户或权限范围，或能等价表达权限范围的可信白名单，避免把别人的检索结果当作命中返回。
- 无序集合先排序再摘要，减少等价请求产生不同 key；摘要用于缩短标识，不是加密，也不能脱敏所有可推断信息。
- 空列表 `[]` 是有效的缓存结果，不能用 `if hit` 判断命中，应区分“未命中”与“命中空结果”。

**项目关联：** 当前 key 包含 query、category、top_n、vector_weight 和排序后的 doc_ids，并有可配置版本前缀；它不是自动随每次文档内容更新而变化的完整版本系统。

### Q037【P1】先更新数据库再删缓存，是否就完全一致？

**参考答案：**
- 不能完全保证。比如读请求先读到旧数据，写请求提交并删缓存，读请求随后又把旧值写回缓存。
- 删除失败也会留下旧缓存。TTL 是最终兜底，不代表满足强一致业务要求。
- 可按需求选择可靠失效消息、重试、版本化 key、CDC、回源协调等；延迟双删也依赖时序，不能当成严格证明。
- 对检索索引，还要协调“数据库记录、文件索引、进程内快照、结果缓存”多个层次，不能只删一层就宣布更新生效。

### Q038【P0】Redis 宕机时，应用应该怎么降级？

**参考答案：**
- 普通缓存可以绕过 Redis 回源，但要限流和控制并发，防止故障被转移到数据库、向量检索或付费模型服务。
- 设置合理的连接 / 读取超时，区分未命中和连接失败，记录故障率与回源压力；不能无限等待或无上限重试。
- broker 不可用时，任务提交不能假装已成功入队；应明确失败、暂存待投递任务或使用 outbox 补发。
- SSE 重放不可用时，应保留本地已生成内容并明确告知恢复失败，而非静默重新生成。

**易错点：** 检索缓存异常可降级，不代表 Redis 的所有用途都可以用一个大 `except` 忽略。

### Q039【P0】Redis 的过期、淘汰、RDB 和 AOF 有什么区别？

**参考答案：**
- **过期回答“何时不再有效”：** 给 key 设置 TTL，到期后逻辑上不再可用。Redis 结合访问时检查与主动扫描清理，不保证到期瞬间就完成物理删除。
- **淘汰回答“内存不足先移除谁”：** 达到 maxmemory 后按策略处理，可能淘汰尚未到期的数据；LRU 偏向最久未使用项，LFU 偏向使用频率低的项，Redis 通常采用近似算法。noeviction 则不淘汰，并可能拒绝需要额外内存的写入。
- **RDB（Redis Database 快照）回答“如何恢复某一时刻的数据”：** 将快照保存为文件，通常较紧凑、恢复方便，但可能丢失最近一次成功快照后的变更。
- **AOF（Append Only File，追加日志）记录写操作以便恢复：** always、everysec 等 fsync 策略在刷盘开销与丢失窗口之间取舍；everysec 通常仍有约一秒的数据风险窗口，实际还受故障和存储行为影响，并非零丢失承诺。
- 前两者是数据保留 / 内存管理策略，后两者是持久化方式，可同时使用。持久化不等于独立备份、自动故障切换或消息绝不丢失，误删也可能被持久化。

**项目边界：** 当前生产 Compose 的 Redis 未挂持久化数据卷；不能宣称容器重建后排队消息必然保留。

### Q040【P1】如何用 Redis 做分布式锁？有什么边界？

**参考答案：**
- **分布式锁**用于协调多个进程 / 机器对同一资源的互斥访问。一个基础租约方案是 `SET key 随机持有者标识 NX PX 租期毫秒数`：NX 表示键不存在才设置，PX 设置有效期；两者与写入在一条命令内完成，防止拿到锁却未设过期时间。
- 返回成功才进入临界区；失败者在预算内等待重试或直接返回。持有者标识必须每次获取锁都唯一，不能只使用固定用户名。
- 释放时用 Lua 原子执行“值是否等于自己的标识 → 相等才删除”，不能先 GET 再独立 DEL，否则两条命令之间锁可能过期并被别人获得。
- 租期到期但旧任务仍在执行时，新持有者可能进入，两个任务会重叠；仅有唯一标识不能阻止过期持有者继续写。续租失败时也不能继续假定自己持锁。
- 严格场景可结合数据库约束或 **fencing token（单调递增的持有权编号）**，由实际存储端拒绝较旧编号的写入；仅生成编号但下游不校验没有保护作用。还需评估 Redis 故障切换导致的锁丢失窗口。
- 对同一数据库中的状态转换，条件 UPDATE 或行锁往往比另引入一把分布式锁简单。

**易错点：** “加了 Redis 锁”不等于“业务恰好一次”，跨系统安全性必须看下游如何约束副作用。

## 5. JWT、认证与 Web 安全

### Q041【P0】JWT 由什么组成？有签名为什么还不能放敏感信息？

**参考答案：**
- **JWT（JSON Web Token）**是承载一组声明的令牌格式。常见签名 JWT 以点分成三段：header、payload、signature，不是所有可能的 JWT 表示形式都只有三段。
- **header（头部）**描述算法、类型等元数据；**payload（载荷）**保存声明，例如 sub 是主体标识、exp 是过期时间、iss 是签发者、aud 是预期接收方；**signature（签名 / 认证值）**用于验证前两段是否被篡改及来源是否可信。
- 前两段通常是 Base64URL 编码，任何拿到 token 的人都能解码，它不是加密。签名解决真实性和完整性，不提供内容保密，因此密码、密钥、完整简历等不应放入普通签名 JWT。
- 服务端应预先配置允许的可信算法，校验签名、有效期、所需声明及 token 类型；不能因客户端 header 声称某种算法就无条件信任它。跨系统还需按设计校验 iss / aud。
- 前端解码 `exp` 只能用于体验优化，不属于安全验签；后端始终独立验证。

### Q042【P0】为什么区分 access token 和 refresh token？

**参考答案：**
- **access token（访问令牌）**是访问业务接口的凭证，使用频繁、有效期相对短，以限制泄漏后的可用时间；**refresh token（刷新令牌）**只用于换取新的访问令牌，通常有效期更长、存放和使用范围更严格。
- 若只有长期 access，泄漏后的风险窗口大；若只有很短的 access，用户会频繁重新登录。两者分离是在安全与会话连续性之间折中。
- **完整流程：** 登录取得两种 token → 携带 access 调用业务接口 → access 到期时调用刷新接口 → 服务端核验 refresh 的类型、有效期和吊销状态 → 返回新 access，采用轮换时同时签发新 refresh → 前端更新凭证，并在满足重试条件时重试原请求一次。
- refresh 若放 HttpOnly Cookie，由浏览器按规则携带，轮换通过 Set-Cookie 更新；refresh 也失效时应重新登录，不能无限刷新。业务接口必须拒绝拿 refresh 冒充 access。
- 这一方案增加服务端状态、轮换、吊销和并发处理成本。有效期没有通用固定值，应按风险、用户体验和撤销需求决定。

### Q043【P0】token 放 localStorage、内存还是 Cookie，各有什么风险？

**参考答案：**
- localStorage 持久且易用，但同源恶意脚本可读；内存不会长期落盘，但 XSS 仍可能在页面运行期间读取或滥用凭证。
- HttpOnly Cookie 不能被 JavaScript 直接读取，但浏览器会按规则自动发送，因此需要考虑 CSRF。
- 常见组合是 access 放内存、refresh 放 HttpOnly Cookie；刷新页面后通过 refresh 恢复登录，具体是否恢复取决于应用启动逻辑。
- `Secure` 约束 HTTPS 传输，`SameSite` 限制跨站发送，`Path` 缩小发送范围；Path 不是可靠的同源脚本安全隔离边界。

**项目关联：** 当前前端使用 token holder，refresh Cookie 为 HttpOnly、SameSite=Strict、Path=/api/auth；Secure 由部署配置控制。

### Q044【P0】refresh token 轮换、jti 和 token family 是如何工作的？

**参考答案：**
- **轮换**指每次成功刷新都用一枚新 refresh 替换旧 refresh；**jti（JWT ID）**标识单枚令牌；**token family**是应用定义的一次登录会话中历代 refresh 的集合，不是 JWT 自动提供的会话机制。
- 一次登录生成 family F 和 token A，刷新得到 B，再刷新得到 C；A、B、C 的 jti 各不相同，但同属 F，服务端记录各自有效期和吊销状态。
- 刷新时核验旧 token，作废旧 jti，签发并记录新 jti，沿用 family，让旧 refresh 正常情况下不能再次使用；旧令牌作废与新令牌记录应在同一事务中完成。
- 若已经作废的 A 被重用，可视为凭证泄漏信号，吊销 F 中仍有效的 refresh，阻断双方继续刷新这轮会话；既有 access 是否立即失效是另一个撤销策略问题。
- family 关联可以保存在数据库，不要求一定写进 JWT；保存 jti / 状态即可，不必存 refresh 明文。

**项目关联：** 当前实现有 jti 轮换和 family 吊销；这描述功能，不代表并发竞争已经完全解决。

### Q045【P1】两个请求同时刷新同一个 refresh token，如何保证只成功一次？

**参考答案：**
- 仅把“查旧状态、吊销、插入新 token”放在事务里，不一定阻止两个事务同时读到未吊销状态。
- 可用行锁串行处理，或条件 UPDATE 抢占未吊销记录并检查影响行数，再在同一事务创建新 token；family 级撤销还需与轮换操作协调。
- 前端单飞减少正常页面的重复刷新，但不能覆盖不同标签页、不同设备和恶意请求，后端仍需并发保护。
- 刷新请求已提交但响应丢失时，重试旧 token 会触发复用检测；严格吊销和有限幂等宽限之间是安全与体验取舍，必须明确定义。

**项目边界：** 当前轮换代码没有显式行锁或条件抢占更新，不要说已经做到“并发刷新严格一次成功”。

### Q046【P0】多个前端请求同时返回 401，怎样避免重复刷新和无限重试？

**参考答案：**
- 用共享的 in-flight Promise 把并发刷新合并成一次，其余请求等待同一个结果；完成后清空 Promise。
- 刷新成功后更新 token holder，原请求用新 token 最多重试一次；刷新失败清理登录态并交互提示。
- 登录、刷新自身不能套用同一套 401 自动刷新逻辑，否则可能递归；403 不应误当 access 过期刷新。
- 已开始消费的 SSE 和有副作用的 POST 不能像普通 GET 一样盲目重发，需按协议设计续接或幂等机制。

**项目关联：** 当前有单飞刷新，SSE 开流前也会预判 access 是否临近过期；单页单飞不是跨标签页分布式锁。

### Q047【P0】JWT 能注销吗？退出登录后旧 access token 会立即失效吗？

**参考答案：**
- 清除前端 token 只影响当前客户端，不会让已复制出去的签名 JWT 自动失效。
- 吊销 refresh 或整个 family，可以阻止继续刷新；已经签发的 access 通常仍可用到过期，除非每次请求还检查黑名单、会话版本或用户状态等服务端条件。
- 即时撤销增加状态查询成本；短 access TTL 则接受一个有限风险窗口，要按业务需求选择。
- Cookie 应使用匹配的名称、Path、Domain 清理；密码应使用 Argon2、bcrypt 等专用密码哈希算法，而不是可逆加密或裸 SHA-256。

**项目边界：** 当前 family 吊销不等于所有既有 access JWT 被即时加入黑名单。

### Q048【P0】XSS 和 CSRF 有什么区别？HttpOnly 能同时解决吗？

**参考答案：**
- **XSS（Cross-Site Scripting，跨站脚本）**是不可信内容被当作脚本，在受害站点的页面上下文中执行。通过按输出位置编码、HTML 清洗、CSP（内容安全策略）和减少危险 DOM 接口等降低风险。
- **CSRF（Cross-Site Request Forgery，跨站请求伪造）**是诱导已登录用户的浏览器向目标站点发送请求，利用浏览器自动附带的身份信息执行操作；不要求攻击者能读取响应，也不要求先在目标站点执行脚本。可用合适的 SameSite、CSRF token 和 Origin 校验等防护。
- **HttpOnly 不能同时解决两者：** 它是 Cookie 属性，只阻止脚本直接读取该 Cookie，不阻止浏览器自动发送 Cookie，也不阻止已经获得同源执行能力的恶意脚本代表用户调用接口。
- LLM 输出、上传 Markdown、引用标题同样是不可信输入；“AI 生成的”不是安全来源。

### Q049【P0】CORS 和 CSRF 有什么关系？带 Cookie 跨域要注意什么？

**参考答案：**
- CORS 是浏览器的跨源访问控制，主要限制脚本读取跨源响应及部分请求，不是认证机制，也不保证阻止所有请求被发送。
- 带凭证跨源请求通常需要前端 `credentials: 'include'`，服务端允许凭证且返回明确的允许 Origin，不能用 `*` 代替。
- Origin 包含协议、主机、端口；Cookie 的 SameSite 看“站点”，两者不是一回事。跨源不一定跨站。
- 真正跨站且需要 Cookie 时常涉及 `SameSite=None; Secure`，但仍可能受浏览器第三方 Cookie 政策影响。生产同域反向代理可简化部署，却不消除 XSS / CSRF 风险。

### Q050【P0】认证和授权有什么区别？如何防止 IDOR 越权？

**参考答案：**
- **认证（Authentication）**确认“你是谁”，例如验证密码或 token；**授权（Authorization）**决定“这个身份能对这个资源做什么”。有合法 JWT 不代表能访问任意 conversation_id、task_id 或 doc_id。
- **IDOR（Insecure Direct Object Reference，不安全的直接对象引用）**指接口使用客户端传入的资源标识，却未验证当前用户对资源的权限，例如换一个消息 ID 就能读到别人的消息。
- 后端必须从可信认证结果获取用户身份，把资源 ID 与 user_id / 可见性条件一起查询，再执行读写；不能信请求体里的 owner_id，也不能只在前端隐藏按钮。
- UUID 只降低猜测概率，不是权限控制。列表、详情、下载、删除、SSE 重放和 RAG 检索都需要一致授权。
- 对私有资源，可统一返回 404 隐藏存在性；明确的管理功能权限不足也可返回 403，按接口语义保持一致。

**项目关联：** 重连不能只凭 stream_id 取缓冲，还要核对它所属会话是否属于当前用户。

## 6. asyncio 与并发控制

### Q051【P0】并发、并行、协程、Task 和事件循环是什么关系？

**参考答案：**
- **并发**是在一段时间内交错推进多个任务；**并行**是在同一时刻真正执行多个任务。例如一个人交替处理两件事是并发，两个人各处理一件可以是并行。
- **协程**是可以暂停、保留执行状态并恢复的计算单元。调用 Python 的 `async def` 得到协程对象，尚未必开始执行；await 它或把它交给 Task 后才会被驱动。
- **Task**是 asyncio 用来驱动协程的任务对象，负责安排后续执行，并保存结果、异常和取消状态。`create_task()` 让协程进入调度，而不是创建一条系统线程。
- **事件循环**是调度器：反复运行就绪回调 / 任务，处理 I/O 就绪和定时器通知，在等待条件满足后恢复相应协程。
- 关系是“协程描述可暂停工作，Task 管理一次执行，事件循环调度 Task”。协程遇到真正需要等待的 await 时让出线程，其他任务趁机执行；大量同步计算不会自动让出。
- 单个事件循环通常在一个线程运行，能重叠多路 I/O 等待形成并发，但不会自动把 CPU 计算分配到多个核心实现并行。

### Q052【P1】顺序 await、`gather` 和 `TaskGroup` 怎么选？

**参考答案：**
- **顺序 await：** `a = await step_a()` 后再执行 `b = await step_b(a)`，适合后一步依赖前一步结果。若先创建了多个 Task 再依次 await，它们仍可能早已并发运行，不能只按 await 的书写顺序判断是否串行。
- **gather：** `await asyncio.gather(fetch_a(), fetch_b())` 会并发调度这两个协程，并按传入顺序返回结果，适合独立任务的结果聚合。默认一个异常会向调用方传播，但其余任务不因此自动全部取消；需要时可显式管理取消，或用 `return_exceptions=True` 收集并处理异常结果。
- **TaskGroup：** Python 3.11 引入的任务作用域，通过 `async with asyncio.TaskGroup() as group` 建组、`group.create_task()` 启动成员，退出作用域时等待成员收尾。一个任务的非取消异常通常触发取消其他成员，并汇总异常。
- **怎么选：** 有依赖顺序执行；彼此独立、需要收集结果时可用 gather；多个任务属于同一次操作、希望一起完成或统一失败清理时优先考虑 TaskGroup，这就是结构化并发的价值。
- 两种并发工具都不会自动限制任务数；大量工作应使用队列和受控消费者，避免一次创建百万个 Task。

### Q053【P0】Semaphore、Lock 和限流分别控制什么？

**参考答案：**
- Lock 用于互斥访问共享资源；Semaphore 允许最多 N 个持有者同时进入，控制在途任务数。
- 每秒请求数限制和并发上限不同：接口很快时，即使并发为 2，也可能一秒请求很多次；速率限制可用令牌桶等。
- `asyncio.Semaphore` 通常只在当前事件循环 / 进程内生效，多个 API worker 各自持有一份，不是全局并发上限。
- 使用 `async with semaphore` 确保异常时释放；控制点应覆盖真正占用外部服务或大内存的阶段。

**项目关联：** Celery 改造后主要由各 worker 的 concurrency 控制消费并发，不能再把旧 API 进程内信号量当作全系统限制。

### Q054【P0】怎样判断任务应该用 asyncio、线程池还是进程 / Celery？

**参考答案：**
- 异步网络 / 数据库 I/O 用 asyncio；必须使用同步 I/O 库时可线程卸载；纯 Python 重 CPU 工作考虑进程。
- 任务很长、需要排队、重试、跨进程隔离或脱离 HTTP 生命周期时，考虑 Celery，而不是只把函数写成 async。
- 远程 PDF 解析主要包含上传、轮询、下载等 I/O；本地 OCR / 模型推理则可能大量占 CPU、GPU 和内存，两者资源策略不同。
- 线程池卸载不等于持久后台任务，进程退出后也不保证完成。

### Q055【P0】超时和取消如何传播？前端 abort 后后端一定停止吗？

**参考答案：**
- **超时**是等待超过预算，**取消**是向运行中的工作发出停止请求。超时机制可以通过取消来收尾，但停止等待和实际工作停止不是同一件事。
- asyncio 的 `Task.cancel()` 请求在后续可处理的执行点注入 `CancelledError`；它不是强杀线程。任务应在 finally 清理资源，然后正常传播取消，不能随意吞掉信号继续运行。
- `asyncio.wait_for()` 到期会请求取消所等待的任务；在正常传播取消的情况下，等待取消收尾后向调用者抛 `TimeoutError`，因此实际耗时可能超过设定值。取消父 Task 通常会传到它正在 await 的子任务，但不会自动停止所有独立创建的 Task；shield 等机制也会改变传播。
- **前端 abort 不保证后端立刻停止：** 浏览器停止读取 / 请求后，后端还需感知断连，并把取消继续传给生产协程或上游客户端；正在运行的同步线程、独立 Celery 任务和供应商推理可能仍继续，甚至继续计费。
- 真正可取消的后台任务需要取消标识、阶段检查、供应商取消能力和明确终态；同时设置连接、读取、单步与全业务预算，避免每层重试重新获得完整超时。

### Q056【P0】为什么要复用 HTTP / 模型客户端？能否把所有对象做成全局单例？

**参考答案：**
- 复用客户端可利用连接池、keep-alive，减少 DNS、TCP / TLS 握手和反复初始化，尤其有利于连续模型请求。
- 复用对象必须满足线程 / 协程安全要求；异步客户端通常应绑定合适的事件循环并在应用关闭时释放。
- 请求专有状态、Session、当前用户不能塞入共享客户端；客户端配置变化也需要明确生命周期。
- Celery 采用多进程时应注意 fork 后连接和客户端的初始化，不能假设父进程已有的连接可以直接安全复用。

### Q057【P1】流式生成器为什么要在 `yield` 前递增序号？断线清理为什么可能延迟？

**参考答案：**
- `yield` 会暂停函数。如果代码写成“yield 当前序号，再执行 seq += 1”，断线关闭可能让后面的递增永远不执行，finally 补帧就可能撞号。
- 更稳妥的顺序是分配当前序号、推进下一序号、缓存事件，再 yield 已分配的帧。
- 同步生成器在线程池里等待上游调用时，客户端断开不一定立刻打断该线程；finally 和 interrupted 终态可能延后。
- 因而单元测试中立即触发关闭的效果，不能直接当成真实网络下的取消时延保证。

<a id="module-7"></a>
## 7. Celery 与后台任务

### Q058【P0】FastAPI BackgroundTasks 和 Celery 有什么区别？

**参考答案：**
- BackgroundTasks 在响应后由当前应用进程执行，适合轻量、可接受进程退出后丢失的工作，不提供完整的持久队列和独立调度。
- Celery 通过 broker 把工作交给独立 worker，便于排队、隔离并发、路由任务和扩容，但增加消息系统与部署复杂度。
- 长时间 PDF 解析、知识库构建适合独立任务；几毫秒且无需可靠执行的小操作未必值得引入 Celery。
- Celery 是否可靠仍取决于 broker 持久化、ack、重试、幂等、文件生命周期和状态补偿，不是装上就不会丢任务。

### Q059【P0】Celery 的 producer、broker、worker、result backend 分别是什么？

**参考答案：**
- producer 发布任务名、参数、task_id 等消息；broker 负责排队与投递；worker 消费消息并执行注册的任务。
- result backend 保存 Celery 结果和状态，可能有过期时间；它与 broker 是不同职责，即使都使用 Redis。
- 业务任务表记录用户归属、业务进度、产物和历史，接口可以以它为权威查询源，而不完全依赖 Celery 的临时状态。
- 任务函数和依赖在 worker 中加载，不能假设 worker 与 API 共用内存对象；参数应可序列化，避免开放不可信 pickle 反序列化。

### Q060【P0】为什么应该先保存任务记录，再投递消息？这样就绝对可靠吗？

**参考答案：**
- 先投递时 worker 可能很快启动，更新尚不存在的任务行，之后 API 再插入 pending，造成任务已经完成但页面永久排队。
- 先落库并确认提交，再投递同一个 task_id，可消除这一先后顺序竞争。
- 但落库与入队是两个系统操作，仍可能“落库成功、投递失败”；如果落库失败被吞掉后仍投递，也会出现无记录任务。
- 更可靠的方案是 **事务 outbox（待投递消息表）**：在同一数据库事务写入业务任务和待发送消息，确保“任务存在”与“有一条消息等待发送”一起提交。独立投递器读取未发送记录，发布到 broker，成功后标记已发送，失败则按预算重试。
- outbox 没有把数据库和 broker 变成同一个事务。如果发布已成功、标记已发送前进程崩溃，下次会再次发送，所以消费者仍必须幂等，并监测长期未投递记录。

**项目关联：** 当前入口按先 `insert_task` 后 `apply_async` 排序；这不等于已实现事务 outbox 或端到端投递保证。

### Q061【P0】什么是任务幂等？只用相同 task_id 就够了吗？

**参考答案：**
- 幂等要求重复执行不会重复产生不可接受的业务副作用，例如重复扣费、重复插入、重复覆盖错误版本。
- task_id 是标识，不是 Celery 自动执行去重承诺；消费者要检查业务状态、唯一约束或执行租约，并设计重复执行结果。
- 文件产物可先写临时文件，再按版本原子发布；数据库状态用条件更新；外部 API 若提供幂等键，应按其语义使用。
- 任务输入必须保留到允许重试的生命周期结束。第一次失败就删除唯一上传文件，会让后续重试没有输入。

**项目边界：** 当前任务存在 finally 清理上传文件的路径，因此不能仅凭 `acks_late=True` 宣称已经具备安全重跑能力。

### Q062【P1】Celery 的 ack、`acks_late` 和 Redis visibility timeout 有什么关系？

**参考答案：**
- **ack（acknowledgement，消息确认）**是消费者告诉 broker“不必再保留这条消息等待重新投递”的信号。它是否意味着业务已完成，要看确认时点，不能只看到 ack 就判断任务成功。
- **提前确认**通常在执行前发生，确认后 worker 崩溃，broker 可能不再投递这项未完成工作。**`acks_late=True`** 将确认推迟到执行之后，降低这一丢失窗口，但若工作已产生副作用、确认前断开，又可能重复执行。
- 任务异常或子进程丢失后的确认 / 重投还受 `task_acks_on_failure_or_timeout`、`task_reject_on_worker_lost` 等配置及 broker 行为影响，不能把 late ack 理解成任何故障都必然重跑。
- **Redis visibility timeout（可见性超时）**是 Redis broker 传输层恢复未确认消息的时间窗口：投递后太久未收到确认，消息可重新进入待消费状态。任务执行超过窗口时，旧任务尚未结束就可能被再次投递；它不是终止任务执行的 time limit。
- “至少一次”允许重复，不是“恰好一次”。应把任务耗时、确认策略、可见性窗口、输入保留、幂等和状态恢复一起设计。

### Q063【P0】任务重试应该怎么设计？所有异常都可以重试吗？

**参考答案：**
- **不是所有异常都重试：** 网络抖动、部分 5xx 和 429 可能自行恢复，可有限重试；参数错误、格式不支持、权限不足通常需先修正原因，原样重试没有意义。
- **指数退避**让连续失败后的等待逐步增长，例如 1、2、4、8 秒并设上限；**随机抖动**在等待时间中加入随机变化，避免大量失败任务在同一时刻重试。若服务返回 Retry-After，应结合其要求与总预算处理。
- Celery 可以通过 `self.retry(...)`，或为明确的异常类型设置 `autoretry_for` 来安排后续尝试；配置最大次数和总截止时间，记录 attempt，耗尽后写入失败终态。不要靠 worker 中无限循环或长 sleep 实现重试。
- 区分 HTTP 请求重试、任务整体重试和用户重新提交；层层重试相乘会放大流量和模型费用。
- 先保证输入仍存在、业务副作用可幂等，再启用任务重试；否则可能重复扣费或在第二次执行时找不到上传文件。异常不能仅记录日志就当作成功返回。

**项目边界：** 下载层的 HTTP 重试与 Celery 任务自动重试不是同一种能力。

### Q064【P0】后台任务状态机和进度接口怎么设计？

**参考答案：**
- 最小状态可以是 pending → running → success / failed，必要时增加 retrying、cancelled；终态应防止被迟到的进度写回覆盖。
- 分离 status、stage、percent、message、error、result 等字段，明确百分比是实际比例还是阶段估算。
- 页面可轮询当前快照；若先 GET 快照再订阅 SSE，应通过与快照一致的事件游标补放订阅间隙的更新，或用后续快照查询校准状态，避免漏掉终态。刷新后用准确 task_id 恢复，任务归属检查必须一致。
- 终态应覆盖最后一条进度文案：不能进度到 100% 仍显示“排队中”。Celery backend 与业务 DB 需明确谁是前端的权威来源。

### Q065【P0】为什么要把不同任务拆成队列？concurrency=1 解决了什么、没解决什么？

**参考答案：**
- 长知识库构建和用户短解析混在同一队列，会让短任务被长任务占满消费者；分队列和独立 worker 可做资源隔离。
- concurrency 控制一个 worker 的执行并发；预取也影响任务公平性，长任务可评估较低 prefetch。
- 单个 worker 的 concurrency=1 只能串行该消费者的执行；再启动同队列第二个 worker，或其他队列也写同一文件，仍可能并发冲突。
- 共享索引的更新还需明确单写者、版本发布或锁策略，不能把“有独立队列”当完整的数据并发保护。

**项目关联：** 当前 Docker 编排包含 resume、knowledge、project 三类消费者，knowledge 为串行配置；不同部署方式的消费者覆盖仍需核对。

### Q066【P0】为什么任务消息只传文件路径，而不直接传 PDF 字节？

**参考答案：**
- 小消息能降低 broker 内存、网络传输和序列化开销；大型文件放共享存储，消息只传可信引用及元数据。
- 本地共享卷要求 API 和 worker 看到同一文件、同一路径；多机部署应换对象存储或共享文件系统，不能假设各机器的本地磁盘相同。
- 文件引用要绑定用户、任务和版本，校验访问权限，并覆盖上传成功但入队失败、重试、任务完成等清理时机。
- 文件写入应先完成再发布消息；否则消费者可能读到不存在或只写了一半的输入。

### Q067【P0】任务一直 pending 或 running，你会怎么排查？

**参考答案：**
1. 查业务任务记录、提交日志和 task_id，确认落库及消息发布是否成功，而不只看页面文案。
2. 查 worker 是否运行、任务是否注册、是否订阅正确队列、broker 地址是否一致，队列是否积压。
3. running 时查实际外部请求、超时、进程存活、资源占用、共享文件、数据库写入异常。
4. 警惕 Celery 的 PENDING 也可能表示“backend 不知道这个 ID”，不一定是消息确实在排队。
5. 对失联任务通过心跳、租约或对账补偿恢复；人工重跑前先检查副作用和幂等条件。

<a id="module-8"></a>
## 8. SSE 与断线恢复

### Q068【P0】SSE、WebSocket 和轮询怎么选？

**参考答案：**
- **SSE（Server-Sent Events，服务端发送事件）**让服务器在一个持续的 HTTP 响应中不断发送文本事件，是服务端到客户端的单向通道。适合 LLM 内容增量和任务进度，通常较容易接入现有 HTTP 认证与代理体系；客户端的新指令可走另一个普通 HTTP 请求。
- **WebSocket**建立可双向发送消息的长连接，适合双方频繁交互、实时协作或音频等场景，但需要管理连接、心跳、重连和应用消息协议。
- **轮询**是客户端按间隔重复发起查询，每次请求读取当前状态，简单且易恢复，适合低频状态更新；代价是多余请求，以及最多接近轮询间隔的额外发现延迟。
- **怎么选：** 低频状态查询优先轮询，持续单向文本输出优先考虑 SSE，频繁双向实时消息优先考虑 WebSocket，而不是按技术新旧选择。
- SSE 不是天然“只支持 GET 的协议”：浏览器原生 EventSource 使用 GET，而 fetch 可以消费 POST 返回的事件流。

### Q069【P0】一条 SSE 消息由哪些字段组成？

**参考答案：** 事件以空行结束，可包含 `event`、`data`、`id`、`retry` 等字段；多行 data 按规则以换行连接，冒号开头是注释，可用于心跳。

```text
id: 42
event: token
data: {"text":"你好"}

```

- **event：** 指定事件名称；不指定时默认按 `message` 事件分发。**data：** 文本载荷，多行 data 以换行连接，是否使用 JSON 由业务约定。
- **id：** 事件标识，原生 EventSource 会据此维护最近事件 ID，并可在重连时发送 Last-Event-ID；业务可把序号放在这里，但服务端必须另行实现存储和重放。
- **retry：** 重连等待时间，值是整数毫秒，例如 `retry: 3000`；原生 EventSource 按规范处理，fetch 客户端必须自行实现，字段本身不会使连接自动恢复。
- 冒号开头的注释行不作为业务事件派发，可用于心跳；事件靠空行分隔。规范允许不同换行形式，自写解析器应明确支持范围。
- TCP / HTTP chunk 与 SSE 消息没有一一对应关系，一次 read 可能只有半条消息，也可能有多条。

### Q070【P0】如何处理 SSE 半帧、多帧和 UTF-8 字符被拆开？

**参考答案：**
1. 字节层使用支持流模式的 TextDecoder，保留跨 chunk 的多字节字符状态，避免中文被截成乱码。
2. 文本层维护缓冲区，只切出完整帧，把最后的半帧留到下次读取。
3. 帧层再解析字段与 JSON，流结束时按协议处理残留；不应把未完成 JSON 当正常业务消息。
4. 还需限制异常缓冲大小，测试空块、多帧、换行拆分和畸形数据。

**项目边界：** 当前解析器支持流式 UTF-8 和以 LF 空行分帧；不要未经验证就声称覆盖 SSE 规范的所有边界形式。

### Q071【P0】为什么不用 EventSource，而用 fetch + ReadableStream？

**参考答案：**
- 原生 EventSource 使用 GET，不能像 fetch 一样自由设置 Authorization 头和 JSON 请求体；对“POST 提交 prompt + Bearer 鉴权”不直接适配。
- fetch 可设置方法、头、请求体、AbortSignal，再从响应 body 逐块读取。
- 代价是自己实现解析、状态机、重连、游标和错误分类，浏览器不会自动替你管理 Last-Event-ID。
- 避免把长期 token 放 URL 查询参数，因为 URL 容易进入日志、历史和监控；连接前与重连时都需正确鉴权。

### Q072【P0】为什么 SSE 中途报错不能直接改成 HTTP 500？

**参考答案：**
- HTTP 状态码和响应头发送后就不能再改；业务异常只能按流协议发 error 事件并结束，或连接异常终止。
- 参数、资源存在性和权限检查应在创建 / 返回流式响应前完成，才能稳定返回 400、401、404 等普通 HTTP 错误。
- 已开流错误应带可识别的业务码和安全信息，不把数据库连接串、堆栈或供应商敏感报文直接送给用户。
- 客户端要区分 HTTP 非 2xx、业务 error 帧、网络中断和主动取消，它们的重试策略不同。

### Q073【P0】SSE 断线重放怎么设计？怎样避免重复文本？

**参考答案：**
- 每条生成流分配 stream_id，事件具有单调递增 seq，服务端按序缓存；客户端保存最后已成功应用的序号。
- 重连携带 `Last-Event-ID` 或 after，服务端重放 seq 更大的事件；客户端仍按 seq 去重，防止边界重叠。
- 应先可靠记录事件再发送，并保证同一序号永远表示同一事件；游标推进要与事件处理成功相协调。
- 事件缓存、stream 到会话的映射都需 TTL 和权限校验，终态也必须可重放。

**易错点：** 只要加了 seq，并不自动获得“恰好一次”；客户端崩溃恢复、漏帧、缓存丢失仍需要边界处理。

### Q074【P0】“断线重连”是否等于“断线后模型继续生成”？

**参考答案：**
- 不等于。第一层能力是重放已经生成且保存的内容；第二层才是把生成任务与连接解耦，让客户端离线时任务继续运行。
- 当前 ResumeAgent 采用降级方案：生成器仍与原请求生命周期相关，断线关闭时尝试补写 interrupted 终态，重连接收已缓冲事件。
- 同步上游调用的清理可能有延迟，所以也不能说断线瞬间模型一定立刻停止。
- 完全后台化需要独立生成任务、事件存储、消费者游标、取消协议和可靠状态机；成本比“缓存一下 token”高得多。

**推荐表述：** “我做的是已生成内容保全和事件重放，不是保证断线后整个回答继续生成完成。”

### Q075【P0】“停止生成”、断线重连和重新生成有什么区别？

**参考答案：**
- 停止生成是用户主动取消，客户端应停止读取和自动重连，保留现有内容并显示中断状态。
- 重连尝试恢复同一个 stream_id，不能再提交原 prompt，否则会创建新任务、产生重复消息和模型费用。
- 重新生成是用户明确发起的新业务动作，需要新的请求标识，并定义旧结果保留 / 替换规则。
- 切换会话或重新发送时，旧回调可能迟到；应检查请求代次或消息 ID，避免旧流写入新消息。

### Q076【P0】后端明明逐 token 输出，为什么浏览器最后一次性收到？

**参考答案：**
- 逐层检查模型供应商、应用生成器、ASGI 服务、中间件、Nginx / CDN 和浏览器消费逻辑，某一层缓冲就会破坏即时性。
- Nginx 常需关闭响应代理缓冲，避免不适合的压缩或缓存，设置合适的读取超时；读取超时通常约束两次上游读取之间的空闲时间，不是请求总时长。
- 长时间没有 token 时可发注释心跳，但同步阻塞的生产逻辑未必能及时发心跳，必要时解耦生产与发送。
- 用带时间戳的服务端日志、直连测试和浏览器事件到达记录定位，不能只看 Network 最终响应体。

**项目关联：** Nginx 配置已包含 `proxy_buffering off` 等 SSE 相关设置；仍需核查真实部署链路是否有额外代理。

### Q077【P0】缓存过期、重连失败或流结束但没收到 done，前端该怎么办？

**参考答案：**
- 缓冲过期 / 无权限按接口返回值停止无意义重试，保留本地草稿，提示内容不完整，并提供用户明确触发的重新生成。
- 短暂网络故障做有上限的退避重连，生产可加随机抖动；主动 abort 不重连。
- 底层 EOF 只代表连接结束，不等于业务成功。没收到协议终态时应按中断或待恢复处理，不能把半段简历显示为完整完成。
- 刷新页面后的恢复还要持久化必要的 stream_id、游标和上下文；只有当前页面变量不够。

**项目边界：** 当前有有界退避和本地内容保全，但不能把它等同于覆盖所有 EOF、页面重启和跨设备恢复场景的完整协议。

## 9. Vue、TypeScript 与 AI 交互

### Q078【P0】Vue 的 `ref`、`reactive`、`computed`、`watch` 怎么选？

**参考答案：**
- **ref 是响应式值容器：** 脚本通过 `.value` 读写，既可放数字 / 字符串，也可放对象。适合 loading、当前消息或需要整体替换的数据；对象值默认也会转为深层响应式。
- **reactive 是对象的响应式代理：** 通过 Proxy 跟踪属性读写，适合结构相对稳定的表单对象。把它的普通数值属性直接解构出来可能失去响应式关联，可用 toRefs 等保持连接；它不用于直接包装一个原始数值。
- **computed 是派生状态：** 自动追踪计算中读取的响应式依赖，依赖不变时复用缓存，例如按消息列表计算可发送状态。计算应尽量纯，不在其中发请求或修改其他状态。
- **watch 是变化后的副作用监听：** 显式指定数据源，在值变化后执行回调，例如切换会话时加载消息、节流保存草稿；默认不是立即执行，可用 immediate 改变初始化行为，异步副作用还需清理过期请求。
- **选择口诀：** 原始状态用 ref / reactive，能由状态算出的值用 computed，状态变化后要“做事情”用 watch。大型不可变数据可评估 shallowRef，但需要通过替换引用等方式显式触发更新。
- token 高频更新仍要缩小渲染范围并测量性能；computed 的依赖若每个 token 都变，缓存同样会失效，不会自动消除计算开销。

### Q079【P0】流式聊天中，组件、composable、store 和类型定义如何分工？

**参考答案：**
- **组件**负责消息、引用、进度的展示和用户交互，不直接承担复杂的字节解析与重试状态机；底层纯解析器专门把字节转换为协议帧，方便独立测试。
- **composable** 是封装可复用有状态逻辑的组合式函数，这里管理连接、取消和重连。复用函数不代表所有调用共享同一份状态；是否共享由状态声明位置和设计决定。
- **store** 集中维护跨组件共享的会话、消息和业务状态，并根据事件更新数据；不要为了组件间通信反复各开一条同样的生成流。
- **类型定义**统一接口请求、消息和事件的数据契约。事件用 `type` 判别联合，例如 token 有文本、error 有错误信息，在分支中可安全缩小类型并检查是否漏处理。
- 流式状态应明确 idle、connecting、streaming、reconnecting、completed、interrupted、failed 等语义，避免多个布尔量形成不可能组合。
- TypeScript 只能约束本地代码，后端载荷仍需必要的运行时校验；可扩展协议要区分可忽略的未知事件与必需字段缺失。

### Q080【P0】长文本流式 Markdown 为什么会掉帧？稳定块分段渲染如何优化？

**参考答案：**
- 每个 token 都对全文做 Markdown 解析、代码高亮、HTML 清洗和 DOM 更新，累计工作量会随长度快速增长。
- 把已完成块与增长中的尾块分开；已完成块缓存 HTML 并保持稳定 key，只对变化片段重复做重处理。
- 切分要考虑代码围栏、列表、表格和引用定义等跨行结构，不能简单把任意空行都视为永远稳定的语法边界。
- 当前项目通过切块、HTML 缓存和 keyed 渲染减少重复工作，但仍会扫描全文切块和计算 key；不能声称整个每帧处理已经严格 O(1)。

**追问：** 超长历史还可分页或虚拟化；单个巨大代码块始终是尾块时，也需要额外优化。

### Q081【P1】如何减少 token 更新造成的重渲染和滚动抖动？

**参考答案：**
- 在接收层缓存增量，按短时间窗或 requestAnimationFrame 批量提交 UI，平衡首字延迟与更新频率。
- 渲染前避免反复做无变化的高亮和清洗，状态按消息 / 块隔离；列表使用稳定标识，而不是变化的随机 key。
- 仅当用户原本在底部附近时自动跟随滚动，用户主动上翻后不要每个 token 强行拉到底部。
- 结束和取消时要处理最后一批缓冲；后台标签页的 rAF 可能被限速，协议状态和数据保存不能完全依赖绘制时钟。

### Q082【P0】为什么 Markdown 渲染后还需要 DOMPurify？

**参考答案：**
- `v-html` 绕过普通文本插值的转义，Markdown 转换器、插件和高亮结果可能带来不安全 HTML 或链接。
- 关闭原始 HTML 是第一层，最终渲染 HTML 再经过允许列表清洗是第二层；必要时限制 URL 协议和外链行为。
- 代码块内容要正确转义，不能直接字符串拼接原文；依赖库需要更新，清洗后不应再拼入未经清洗的内容。
- CSP 是补充防线，不代替输出清洗和权限控制。

**项目关联：** 当前使用 markdown-it 禁用原始 HTML，再经 DOMPurify 清洗后用于渲染。

### Q083【P0】工具调用时间线和 RAG 引用卡片应该怎样设计？

**参考答案：**
- 时间线展示检索、选材、生成等用户能理解的阶段；开始、结束、失败、耗时可通过结构化事件关联，而不只拼一串状态文本。
- 引用卡片携带可信的 doc_id、chunk_id、标题和来源映射，用户可回到实际证据；不能只让模型自由编一个 URL。
- 任务结束要结算最后一个进行中的阶段，重放不能生成重复条目；复杂并行工具需要 call_id，不能只按文本去重。
- “检索到的来源”和“答案明确使用的证据”要区分，显示一张卡片不等于已经验证答案中的每个事实。

**项目关联：** 当前前端基于状态事件形成时间线并展示检索来源，不应夸大为已实现任意并行工具调用的完整 tracing。

### Q084【P0】为什么页面刷新后任务和已有简历上下文容易丢失？

**参考答案：**
- Pinia / 组件内存随着页面重载重建；后端有任务记录，也不会自动知道用户刚才关注哪一个 task_id。
- 同标签页恢复可用 sessionStorage 保存必要的任务标识、草稿和上下文，加载后向后端校验身份与当前状态。
- 不要盲选“任务列表最新一条”，多标签页、不同任务类型和并发提交都会选错。
- 本地存储只是恢复线索，不是授权依据；简历属于敏感内容，应按产品需要控制保留范围、清理时机和写入频率。

### Q085【P0】TTFT 怎么定义？为什么首事件快不代表首 token 快？

**参考答案：**
- TTFT（Time To First Token）是首 token 延迟。前端常见口径是从用户提交到首个可展示内容增量到达；首个 status / conversation 事件只代表请求有响应，不能当作回答首 token。
- 供应商首 token、后端生成调用首 token、前端请求到首 token 是不同口径，后者还包含认证、意图识别、检索和网络。
- 用户真正看到还要经过框架更新和浏览器绘制；如需测可见延迟，应另设首内容渲染指标，而不把收到帧直接当成完成绘制。
- 使用单调计时器，按请求关联分阶段数据；看 P50 / P95、样本量、缓存冷热、模型和输入长度。P50、P95 分别表示约 50%、95% 的样本耗时不超过该值，不能只用平均数掩盖长尾。

**项目边界：** 当前前端记录 send 到首个 token 事件；后端快速问答日志中的首 token 从生成调用开始计，两者不能直接当成相同指标。简历深思路径的首个 token 事件承载完整简历，计时接近等待完整结果的时间，应与快速问答分开统计。

<a id="module-10"></a>
## 10. RAG 与知识库

### Q086【P0】什么是 RAG？和微调、直接塞长上下文有什么区别？

**参考答案：**
- RAG（Retrieval-Augmented Generation，检索增强生成）在生成前从外部知识中检索证据，再把相关内容提供给模型；主要改变本次推理获得的参考资料，不要求更新模型参数，适合知识更新、来源追溯和访问范围控制。
- 微调通过训练更新模型参数，常用于调整行为、风格或任务能力；虽然也可能学到知识，但不适合当作频繁更新的精确事实数据库，仍可结合检索。
- 直接塞长上下文是把全文等资料直接放进本次输入，不先检索筛选，也不更新模型参数；实现简单，但受上下文窗口、成本、噪声和长上下文利用能力影响，小文档集合也可能适合。
- 三者可以组合。RAG 不保证没有幻觉，检索错误和提示词设计错误仍会传递到生成结果。

### Q087【P0】一个完整知识库入库链路有哪些阶段？

**参考答案：**
- 文件接收与校验 → 文档解析 / OCR → 清洗与保留结构 → 分块 → 元数据与权限绑定 → embedding / BM25 建索引 → 验证与发布。
- OCR（Optical Character Recognition，光学字符识别）把扫描图像中的文字识别出来；embedding 把文本编码成向量，供后续按语义相似度检索；BM25 则基于分词后的词项统计建立检索索引。
- 表格、标题、页码和代码结构会直接影响召回；不能把 PDF 解析当成无损复制文本。
- 需要记录来源、版本、doc_id、chunk_id 和处理状态，支持增量更新、删除、失败重跑与引用回溯。
- 索引构建失败不能假报成功；发布应避免查询读到半套新索引，解析临时产物也不应混入知识源目录。

**项目关联：** 简历 PDF 走远程解析与课程文档本地构建是不同链路，不应笼统说所有 PDF 都采用同一资源方案。

### Q088【P0】chunk size 和 overlap 怎么选？越大越好吗？

**参考答案：**
- chunk size 是每个文本块的目标长度或长度上限；overlap 是相邻块重复保留的文本长度，用于保留跨边界信息。两者都不是越大越好。
- 小块定位精确、噪声少，但可能丢掉上下文；大块通常保留更多上下文，却更难聚焦，消耗更多 token。
- overlap 缓解边界截断，但会增加存储、embedding 成本和重复召回；不能靠无限重叠解决切分质量。
- 优先遵循标题、段落、代码和表格等语义结构，再用 token 上限约束；长度单位要明确，字符数不等于 token 数。
- 用实际问题集测召回与答案质量，再调参数；可以保留父文档或邻接块供需要时扩展上下文。

### Q089【P0】BM25 和向量检索各擅长什么？中文分词为什么重要？

**参考答案：**
- BM25 基于词项匹配、词频、逆文档频率和长度归一化，对函数名、产品名、错误码等精确关键词有效。
- 向量检索用 embedding 模型把查询和文档编码到兼容的向量空间，再按相似度或距离查找近邻；擅长语义相似和不同说法的匹配，但可能漏掉少见标识符，或召回“意思接近但事实不对”的内容。
- 中文通常没有空格标明词语边界，不能简单按空格分词；切错技术术语会改变匹配词项与词频统计，使 BM25 漏掉相关文档或召回噪声。文档和 query 的分词、归一化方式需一致，并保护技术术语及必要的符号组合。
- 混合检索让两者互补，但融合质量仍需验证，不能认为两份结果拼起来就一定优于单路。

### Q090【P0】FAISS 是数据库吗？余弦相似度、内积和 L2 怎么区分？

**参考答案：**
- FAISS（Facebook AI Similarity Search）主要是向量相似性搜索库，不是完整的业务数据库，不自动提供业务事务、权限、备份和文档生命周期管理。
- 对向量 x、y，内积为 `Σ(xᵢ × yᵢ)`，既受方向也受模长影响；余弦相似度为 `x·y / (‖x‖ × ‖y‖)`，只比较方向，要求向量非零；L2 是欧氏距离 `√Σ(xᵢ − yᵢ)²`，比较空间中的直线距离。
- 将查询和文档向量都归一化到单位长度后，内积等于余弦，且 `L2² = 2 − 2 × 余弦相似度`，因此按 L2 升序与按余弦降序得到对应排序。
- L2 距离越小越近，内积或余弦相似度越大越相似。FAISS 的 L2 度量通常返回平方距离，虽不影响排序，但不能当作已经开平方的距离使用；更不能只看字段叫 distance 就决定排序方向。
- 查询和文档必须使用兼容的 embedding 模型、维度与归一化方案；更换模型通常需要重建索引。

**追问：** Flat 搜索直接扫描向量，简单且精确；ANN（Approximate Nearest Neighbor，近似最近邻）索引通常以部分召回率换搜索速度，内存变化取决于索引结构及是否压缩。是否需要 ANN 应按数据量和延迟目标决定。

### Q091【P0】混合检索怎么融合？为什么不能直接把两个分数相加？

**参考答案：**
- 基本流程是分别召回候选 → 按稳定的 doc_id / chunk_id 合并去重并保留各路分数或排名 → 计算融合分数 → 排序截断；必要时用 reranker 对候选与问题的相关性重新打分、精排。
- 向量相似度与 BM25 分数的范围和分布不同，直接加权可能由某一路主导；即使权重写 0.5，也不代表两路贡献相等。若向量侧返回距离，还须先统一“越大越好”或“越小越好”的方向。
- 可以归一化 / 校准分数再加权融合，也可采用 RRF（Reciprocal Rank Fusion，倒数排名融合），减少不同量纲的影响。
- RRF 对同一候选累加各路的 `1 / (k + rank)`；rank 通常从 1 开始，k 是平滑常数，不是召回条数，该路未召回时贡献为 0。它降低标度问题，但不直接利用分数差距，参数与效果仍需评估。
- 融合、召回数量和精排都要一起评估相关性、延迟与成本，不能仅凭使用了更多检索器就认定效果更好。

**项目边界：** 当前实现是向量与 BM25 原始分数的简单加权，不是 RRF 或已接入 cross-encoder 精排；这可以作为明确的后续优化点。

### Q092【P0】什么是分层检索？为什么先选课程再检索知识点？

**参考答案：**
- 先利用课程目录 / 摘要确定相关文档和知识点，再在选中的 doc_ids 中检索细粒度片段，可减少全库噪声。
- 多课程素材若只做全局前 k 截断，可能被一个课程占满；按课程限额、轮询交错合并能改善覆盖度。
- 代价是前置选择可能选错，增加模型调用和延迟；应保留受权限约束的降级路径并评估选点召回率。
- 公平覆盖不等于相关性最高：课程数量、重要性与上下文总预算需要一起考虑。

**项目关联：** 当前 `retrieve_by_plan` 有定向 doc_ids 检索、去重、课程配额与轮询合并，不是简单把各路列表顺序拼接。

### Q093【P0】多用户 RAG 怎样避免检索到别人的文档？

**参考答案：**
- 身份在后端验证，权限范围转换为可信文档白名单 / 元数据过滤，在候选召回阶段就约束，不能只靠提示词说“不许看别人的”。
- 向量、BM25、目录选择、项目素材、缓存和原文下载应采用一致权限规则；任何降级路径都不能放宽范围。
- 空白名单必须表示“没有可访问内容”，不能被 `if doc_ids` 一类逻辑误解释为“不限制”；上层调用和底层检索都要核对语义。
- 权限变化要影响缓存和索引可见性，避免用户被撤权后仍命中旧结果。

**易错点：** 先全库召回再让模型自行剔除，已经把私有数据暴露给了模型上下文，不是安全隔离。

### Q094【P1】知识库如何做增量索引和安全发布？

**参考答案：**
- 用稳定 doc_id 配合内容 hash / 版本判断变化；mtime 简单便宜，但不一定可靠表达内容身份。解析器、切分策略或 embedding 模型版本变化，也可能要求重新构建。
- 跳过未变文档，重新解析、分块和索引新增 / 变更文档；在待发布版本中移除变更文档的旧块、写入新块，删除文档则移除其索引与元数据，避免新旧内容同时被召回。
- 全库重建通常实现最简单；文档级增量能减少计算，且比 chunk 级增量更容易实现。chunk 级增量可进一步减少 embedding，但需解决分块边界变化、稳定 ID 和旧块清理。
- 新索引先构建到临时位置并验证数量、维度和元数据对应关系，再原子切换版本指针；查询应固定读取一个完整版本，多个产物必须彼此匹配，单文件 replace 不等于多文件事务。
- 更新后还需刷新进程内检索器和结果缓存，清理孤儿块、失效引用与不再被使用的旧版本；构建失败时继续提供旧的完整版本，不发布半成品。

### Q095【P0】如何判断 RAG 效果提升，而不是“感觉回答更好了”？

**参考答案：**
- 建立包含真实岗位问题、精确术语、多文档问题、无答案问题和越权测试的固定数据集，标注期望证据与关键答案点；固定切分版本和评测口径，用同一测试集比较基线与改进方案。
- 检索侧：Recall@k 是前 k 条命中的相关证据数 / 全部标注相关证据数；MRR 是各问题“首个相关结果排名倒数”的平均值，未命中记 0；nDCG 按排名位置折损分级相关性得分，再用理想排序得分归一化。应说明 k 和证据标注单位，无相关证据的问题单独评测，避免分母为 0。
- 生成侧：正确性看事实和答案要点是否正确，忠实度看回答能否由给定证据支持，引用准确性看所引片段是否支持对应断言；还要测无证据时的拒答与用户任务完成度。回答碰巧正确，不代表它忠实使用了检索证据。
- 同时记录 TTFT、总耗时、token 成本、缓存命中和失败率，做单变量或消融对比，例如 BM25、向量、混合、分层检索；同时检查失败案例，而不是只看总分。
- LLM-as-judge 是用模型按评分规则辅助评审，但有偏差，应固定评审规则并人工抽检；不要只挑成功样例，也不要把训练 / 调参集当独立测试集。

## 11. Agent 编排与 LLM 工程

### Q096【P0】普通 LLM 调用、工作流和 Agent 有什么区别？为什么用 LangGraph？

**参考答案：**
- 普通 LLM 调用通常是应用按预定位置发起一次输入到输出的生成，不代表输出内容确定；工作流把多个步骤按明确规则组织；Agent 则让模型在一定范围内动态选择动作、工具或后续路径。
- LangGraph 是有状态的图编排框架：节点执行具体步骤并返回状态更新，边连接步骤，条件边根据当前状态选择下一步；既能表达固定流程，也能表达模型决策驱动的循环。
- 它适合多步骤、分支和需要检查执行过程的场景；选择框架是为了流程可读性、状态边界与扩展能力，不是“用了 LangGraph 就自动有智能体、记忆和容错”。状态持久化和恢复需要配置相应机制。
- 对确定性强的业务，受控工作流往往比无限 ReAct 循环更可预测、更容易测试。

**项目边界：** 当前既有图定义，也有显式编排的 `run_stream` 路径；不要把流式入口描述成已经统一使用图 checkpoint 驱动的执行引擎。

### Q097【P0】Agent state、聊天记录和长期记忆有什么区别？

**参考答案：**
- state 是工作流执行时传递和更新的状态，例如意图、检索结果和草稿；其是否跨轮保留取决于配置，不能因为定义了 state 就认为已持久化。
- 聊天记录是按会话保存的用户与助手消息，属于历史业务数据；模型是否“记得上一轮”，取决于下一次调用有没有注入历史、摘要或相关记忆，不取决于数据库里是否存在消息。
- 长期记忆是跨多次交互、甚至跨会话保留并按需检索注入的信息，例如用户偏好和确认过的事实；不是把全部聊天原文无限塞进上下文，还需要提取、更新、遗忘和权限策略。
- checkpoint 是在执行边界保存的状态快照，可用于恢复流程或保留同一执行线程的状态；它不是自动形成跨会话长期记忆的机制。
- 多轮上下文会增加 token、隐私与冲突处理成本，可按窗口、摘要、相关历史选择等方式控制。

**项目关联：** 当前会话消息已落库，但模型侧没有据此自动注入跨轮历史，不应声称已实现完整多轮记忆。

### Q098【P0】Function / Tool Calling 到底是谁执行工具？如何保证安全？

**参考答案：**
- 模型通常只输出工具名和结构化参数，由应用校验并实际调用，再把结果交回模型；模型不会因为输出 JSON 就直接获得系统权限。
- 工具采用允许列表和参数 schema，服务端再次检查用户权限、路径、目标范围和资源预算。
- 读取类工具和有副作用的写入工具要分级，重要动作需要确认、幂等和审计；工具超时、错误输出也要结构化。
- 对多次调用设置步数、时间和费用上限，工具结果只返回必要信息，不泄露密钥或完整内部堆栈。

**易错点：** 函数名字叫 tool，或代码里封装了工具类，不代表模型已具备自主选择任意工具的能力。

### Q099【P0】什么是提示注入？为什么“在 system prompt 写不许泄密”还不够？

**参考答案：**
- 用户输入、检索文档或工具返回可能夹带“忽略规则、执行其他动作”等指令，诱导模型把低信任数据当成高权限命令。
- 提示词应明确数据边界，但模型层约束不是可靠的权限执行机制；真正权限、允许的工具、参数与数据范围要由代码控制。
- 最小权限、工具白名单、敏感动作确认、输出校验和数据最小化一起降低风险，避免把密钥放进模型可见上下文。
- 简历和知识库原文应当作为待处理资料，不应获得修改系统行为的权力；测试也应包含恶意文档样例。

### Q100【P0】如何避免简历生成中的幻觉和经历造假？

**参考答案：**
- 区分用户真实履历、课程知识、项目素材和岗位要求。岗位要求是优化方向，不是用户已经具备该经历的证据。
- 已有简历作为事实骨架，允许改写表达、结构和与岗位相关的强调，不凭空增加公司、年限、职级、业绩数字。
- 缺失信息标记待补充或询问用户；生成后按事实清单、来源和结构要求校验，关键内容由用户确认。
- 降低 temperature、加 RAG 或写强提示都只能降低风险，不能保证事实完全正确。

### Q101【P0】LLM 应用如何同时优化延迟、质量和成本？

**参考答案：**
- 先分解请求时间：鉴权、意图判断、检索、连接建立、首 token、完整生成和渲染，定位主要瓶颈。
- 轻量分类 / 改写可选快模型或在模型支持时关闭不必要的 thinking；复杂生成保留足够能力，避免全链路都用最慢模型。
- 复用客户端、缓存确定性中间结果、限制上下文、合并或并发独立调用；每项优化都要比较质量回归。
- 流式输出降低感知等待，不一定缩短全部生成时间；检索缓存命中也不等于最终回答免模型调用。

**项目边界：** 快速问答是 token 流式；简历深思路径主要输出阶段进度，最后返回完整简历，不能说所有生成阶段都逐 token 流式。

### Q102【P1】Agent 如何处理循环、工具失败和供应商故障？

**参考答案：**
- 设置总步数、总耗时、token / 金额预算，以及单个工具超时，避免模型反复执行同一种无效动作。
- 对错误分类：可恢复网络错误有限重试，参数错误可反馈模型修正，权限错误不能通过换工具绕过。
- 降级路径需保持事实与权限边界，例如向量服务失败可用受同样白名单限制的 BM25，而不是回退全库查询。
- 提供明确失败或部分结果，保留可诊断的阶段状态；引入多模型切换还要考虑响应格式、能力差异和重复计费。

## 12. Docker、部署与 Linux

### Q103【P0】Docker 镜像和容器有什么区别？多阶段构建为什么能瘦身？

**参考答案：**
- 镜像是分层的运行模板，容器是基于镜像启动的进程与隔离环境；容器可写层通常不应用于长期业务存储。
- 多阶段构建在构建阶段安装 Node 等工具，只把编译产物复制到运行阶段，避免把完整构建工具链带上线。
- 先复制依赖清单、安装依赖，再复制频繁变化的源码，可利用层缓存；`.dockerignore` 防止无关文件和密钥进入构建上下文。
- 小基础镜像、生产依赖、非 root 运行和固定可追踪版本都值得评估，但瘦身不能删掉运行时真正需要的库。

**项目关联：** 当前 Dockerfile 先构建 Vue 前端，再复制产物进入 Python 运行镜像；新增运行依赖还需同步生产依赖清单。

### Q104【P0】Compose 容器之间为什么不能用 localhost 通信？健康检查有什么边界？

**参考答案：**
- 容器内 localhost 指当前容器自己；同一 Compose 网络通常通过服务名和容器端口访问，例如 API 连接 redis 服务的 6379。
- 宿主访问使用发布端口，宿主端口与容器端口可以不同；数据库和 Redis 不必全部暴露公网。
- depends_on 的健康条件帮助控制初始启动顺序，但不保证依赖之后永远健康；应用仍需处理断线、超时和重连。
- 普通 Compose 标记 unhealthy 不一定自动重启容器，重启策略与编排器行为要分清；HTTP 健康不等于 Celery 队列有消费者。

### Q105【P0】bind mount 和 volume 有什么区别？为什么挂载后数据“消失”了？

**参考答案：**
- bind mount 映射明确的宿主路径，便于开发和手工管理，但受宿主路径与权限影响；named volume 由 Docker 管理生命周期。
- bind mount 会遮盖镜像中目标位置的内容，不会自动合并；空宿主目录覆盖内置索引时，应用会表现成没有知识库。
- 空 named volume 首次挂到已有内容的容器目录时，Docker 默认会复制目录内容到卷，`volume-nocopy` 可禁用这一行为；这与 bind mount 不同。
- API 与 worker 需要读取同一上传文件时，应共享正确挂载；多机扩容要重新设计共享存储，而不是只复制 compose 文件。
- 备份应覆盖数据库和运行数据；删除容器不一定删除卷，但 `down -v` 等操作可能丢掉卷数据，不能作为常规排障第一步。

### Q106【P0】从浏览器访问 HTTPS 域名到 FastAPI，链路怎样走？

**参考答案：**
- DNS 解析到服务器，浏览器建立 TLS 并验证证书，Nginx 终止 TLS，再把 API 请求代理到本地 / 内网应用；前端静态资源可同域提供。
- 需要检查域名、证书覆盖、80 / 443、防火墙、证书续期、转发头和应用对代理头的可信范围。
- 生产启用合适的 Secure Cookie，静态带 hash 资源可长缓存，入口 HTML 要避免长期缓存旧资源引用；SSE 路径单独考虑缓冲和超时。
- HTTPS 保护传输，不替代登录鉴权、对象归属校验或数据库访问隔离。

### Q107【P0】如何设计 GitHub Actions 的 CI/CD 流水线？

**参考答案：**
- CI（Continuous Integration，持续集成）在代码变更时自动构建、检查和测试；CD 可指持续交付（Continuous Delivery，保持可发布，生产发布可需人工批准）或持续部署（Continuous Deployment，通过门禁后自动上线），要明确采用哪一种。
- 在 `.github/workflows/*.yml` 中声明触发事件、jobs 和 steps：例如 PR 触发验证，受保护分支或发布标签触发发布；用 job 的依赖关系保证验证成功后才能进入发布，不是所有 job 默认顺序执行。
- PR 阶段安装可复现依赖，做类型 / 静态检查、单元与集成测试、前端构建；测试通过后才把产物标记为可发布。
- 发布阶段使用提交 SHA 标签或镜像内容 digest 标识版本，并通过仓库策略禁止覆盖版本标签；把同一份已验证产物推到环境，执行兼容迁移、健康检查和关键冒烟测试。
- 权限最小化，密钥放受控 secret，不能回显日志；防止不可信 PR 获取部署权限，生产部署可使用环境审批和并发控制。

### Q108【P1】发布如何回滚？数据库也能像镜像一样切回吗？

**参考答案：**
- 应用回滚可切换到上一不可变镜像 / 版本，但需要确认旧代码仍兼容新 schema 和现有数据。
- 数据库删除列、重写数据等可能不可逆，不能因为写了 downgrade 就认为无损；常用向前修复和兼容扩展 / 收缩迁移。
- 发布前明确备份、恢复演练、迁移执行者和健康门槛；迁移不宜让所有副本启动时同时跑。
- 对长连接和后台任务进行排空，保留输入与中间状态；worker 更新时要考虑旧任务能否由新代码安全继续处理。

### Q109【P0】如何用 systemd 管理 Python 服务？为什么读不到 `.bashrc` 的变量？

**参考答案：**
- systemd 是 Linux 的系统与服务管理器，可用 service unit 定义如何启动、停止和重启服务，并管理开机启动。通常在 `/etc/systemd/system/app.service` 创建应用的 unit 文件，app 为示例服务名。
- `[Unit]` 声明描述与启动依赖；`[Service]` 指定 User、WorkingDirectory、ExecStart、EnvironmentFile 和 Restart 策略；`[Install]` 常设 `WantedBy=multi-user.target`，供 enable 建立开机启动关系。用户、虚拟环境及目录须预先准备好并具有合适权限。
- ExecStart 使用虚拟环境中可执行文件的绝对路径，例如 `/srv/app/.venv/bin/uvicorn src.api.main:app`，不依赖先执行 activate；路径与应用入口需按实际项目调整。生产避免默认 root 运行全部服务。
- systemd 不等同于登录交互 shell，不会自动加载用户 `.bashrc`；应用需要的变量应通过 `Environment=` 或 `EnvironmentFile=` 显式提供，环境文件不写 shell 的 `export`，敏感文件应限制读取权限。
- 保存 unit 后执行 `sudo systemctl daemon-reload`，首次用 `sudo systemctl enable --now app.service` 启用并启动；修改已有服务后用 `sudo systemctl restart app.service` 使新配置生效。enable 只负责开机启用，单独执行并不立即启动；daemon-reload 也不会重启运行中的进程。
- 用 `systemctl status app.service` 看状态，`journalctl -u app.service -n 200 --no-pager` 或 `journalctl -u app.service -f` 查日志，并验证服务实际环境和监听端口，不要只检查交互终端里的变量。

### Q110【P0】Linux 服务 CPU 打满、僵住或端口占用，怎么排查？

**参考答案：**
- 先 `top` / `htop`、`ps` 看进程、线程、CPU / 内存，结合请求量、日志判断是正常计算、死循环、I/O 等待还是进程反复重启；确定 PID 后可用 `top -H -p PID` 缩小到高占用线程。
- 用 `ss -tlnp` 或 `lsof -i :端口` 查监听进程，确认 PID 和归属，再判断是否启动了重复服务。
- 僵住时查线程栈、锁等待、外部连接和数据库等待；例如工具已安装且权限允许时，用 `py-spy dump --pid PID` 查看 Python 栈，间隔取几次判断是否卡在同一位置，必要时用 `strace -p PID` 观察系统调用，并结合数据库活动与锁等待定位。
- 调试附加与采样有权限和开销要求，应控制范围，避免采集敏感参数；有 CPU 使用不等于能接受请求，没有 CPU 使用也不代表正常。
- 需要停止时优先通过服务管理器或 SIGTERM 优雅退出；SIGKILL 无法被捕获，可能留下半成品，不应一上来 `kill -9`。

### Q111【P0】磁盘没满却写不进去、权限不足，分别怎么查？`chmod 755` 是什么意思？

**参考答案：**
- `df -h` 看块空间，`df -i` 看 inode，`du` 查目录占用；还要考虑配额、只读挂载、保留空间，以及已删除但仍被进程占用的文件，后者可用 `lsof +L1` 辅助定位。
- 权限数字分别对应 **所有者、所属组、其他用户**，不是“管理员、用户组、普通用户”；r/w/x 分别为 4/2/1，所以 `chmod 755 目标` 是把目标权限设为 rwx / r-x / r-x。
- 目录的 x 表示可进入 / 遍历，文件 x 表示可执行；新建文件通常要求父目录有 w+x，改已有文件内容要求文件本身可写且路径可遍历。脚本还可能因解释器路径或挂载 noexec 无法直接执行。
- 用 `ps -o user,group -p PID` 查服务实际身份，`namei -l /目标路径` 逐级检查父目录，`stat /目标路径` 看所有者与权限；再核对附加组、容器挂载 UID/GID，必要时检查 ACL 或安全模块限制，而不是直接 `chmod -R 777`。

## 13. 测试、可观测性与排障

### Q112【P0】单元测试、集成测试、端到端测试各验证什么？怎样证明接管了 AI 生成代码？

**参考答案：**
- 单元测试验证小范围逻辑，如 SSE 分帧、缓存 key、状态转换；集成测试验证数据库、Redis、路由与服务之间的真实契约。
- E2E 从用户操作或公开接口走完整链路，验证登录、任务提交、状态恢复、流式展示等用户结果。
- mock 适合隔离慢且不可控的外部模型，但不能用 mock 的成功证明真实消息队列、外键、断线和代理缓冲正确。
- 接管代码应能追踪调用链、解释测试保护点、独立修改并写回归测试；用故意破坏一处逻辑让对应测试变红，验证测试确实有约束力。

### Q113【P0】为什么 SQLite / mock 测试通过，PostgreSQL / Redis 联调还会失败？

**参考答案：**
- 数据库方言、外键启用方式、类型、时区、事务隔离、锁和异步驱动不同；关键迁移、约束及并发行为应在隔离的真实 PostgreSQL 上验证。
- mock 往往跳过 Redis 的真实序列化、TTL 到期、并发竞争、网络认证及连接超时；内存假对象返回成功，不能证明不同进程之间的缓存和队列可用，也不能证明故障恢复正确。
- 测试必须替换代码实际引用的 Session 工厂、客户端或配置单例；只 patch 一个新创建的配置对象，未必影响已导入模块。
- 使用独立测试库、Redis namespace 和任务队列，避免测试写入真实业务数据；结束后只清理本次创建的资源。
- 不只断言 200：还要核对记录内容、user_id、终态、产物以及越权返回，防止“请求成功但没做事”的假阳性。

### Q114【P0】SSE、取消和后台任务怎样测试才不容易假通过？

**参考答案：**
- 解析器用可控字节块覆盖中文多字节拆分、半帧、多帧、id、坏 JSON；状态层覆盖重复 seq、缺终态、主动取消和缓冲过期。
- 取消测试不只看前端停更：先明确契约是停止接收、请求后端中断，还是确认任务已停止，再检查相应后端状态、资源释放和后续执行情况。覆盖重复取消、完成与取消竞争、迟到帧不覆盖终态；不能把浏览器 abort 当作供应商推理已经停止的证据。
- 路由测试验证开流前 401 / 404，流中错误验证 error 事件；不要关闭测试客户端的服务端异常传播后只看 HTTP 200。
- 实际服务器 + 流式 HTTP 客户端 / 浏览器测试代理链路、到帧时间和断网恢复，内存 TestClient 可能缓冲，不能证明实时性。
- Celery 用真实隔离 worker 验证入队、执行、状态和共享文件；eager 模式跳过了 broker 与进程边界，不能当完整集成测试。

### Q115【P0】日志、指标、追踪有什么区别？AI 应用最该观测什么？

**参考答案：**
- 日志记录具体事件和错误上下文；指标统计流量、延迟、失败率等趋势；追踪关联跨服务请求中各阶段的耗时和因果关系。
- 重点观察请求量、P50 / P95 延迟、TTFT、完整生成耗时、模型 token / 费用、检索命中、队列等待、执行时长、重试和失败率。
- 用 request_id、conversation_id、stream_id、task_id 关联日志；指标标签避免直接放用户 ID 或完整 query 等高基数 / 敏感值。
- 记录 cache hit / miss / error，防止异常降级掩盖缓存失效；对简历、token 和密钥做最小化与脱敏。

**项目边界：** 当前已有普通日志、阶段耗时和前端 TTFT 等记录，不应说已没有任何性能观测，也不应夸大成已接入完整 Prometheus / tracing 平台。

### Q116【P0】线上出现“前端正常，但接口一直慢 / 500”，你怎么分层定位？

**参考答案：**
1. 确认影响范围、起始时间和最近发布，保留请求标识；区分静态页面可访问与 API / worker 可用。
2. 查看浏览器状态码、响应、到帧时间与控制台，再查 Nginx access/error、应用及 worker 日志。
3. 判断慢在连接、鉴权、数据库池、SQL、Redis、队列等待、模型供应商还是渲染；用超时和阶段指标缩小范围。
4. 核实运行中镜像、依赖版本、环境变量、迁移 revision 和挂载，而不只检查宿主机代码。
5. 先采取有依据的限流、降级或版本回滚，再修复根因、补测试与告警；不把重启或清库当万能答案。

### Q117【P0】请用一分钟介绍 ResumeAgent，以及你从前端向全栈补了什么？

**参考答案示例，按本人实际负责内容调整：**

### Q118【P0】简历写“首 token 11s → 0.6s”，面试官追问时怎么回答？

**参考答案：**

- 用阶段日志或测量记录证明，例如轻任务关闭 thinking、客户端复用、检索缓存等；同时报告答案质量是否回归。

### Q119【P0】项目里最有价值的一次技术取舍是什么？怎样按“背景—方案—结果”讲？

**参考答案模板：**
- **背景：** 先说用户问题，而不是术语。例如“PDF 解析很慢，用户不知道是否成功，页面重载后找不到正在做的任务”。
- **方案：** 解释原方案限制、为什么选择任务化，讲清先落库再入队、task_id、独立消费者、业务状态查询，以及前端恢复。
- **结果：** 只说有证据的结果，例如请求不必等待解析完成、刷新可查同一任务、短任务不再被同队列长构建直接占住消费者；有数据再补延迟与成功率。

**可替换故事：** 缓存优化、稳定块渲染、JWT 轮换、降级断线恢复。选择你能解释代码、复现实验和说清失败路径的故事。

### Q120【P1】如果用户量增长十倍，你会先做什么？当前项目离更可靠的生产系统还差什么？

**参考答案：**
- 先定义 SLO（Service Level Objective，服务等级目标），即在明确统计窗口和范围内希望达到的成功率、P95 延迟等指标；再建立容量模型，把用户量换成峰值请求量、同时生成数、任务到达率与资源需求，用户十倍不代表所有资源都应直接乘十。
- 逐档增加负载，通过压测定位模型调用、API、数据库连接池、队列等待、索引内存或前端渲染的实际瓶颈，同时观察成功率、延迟与成本，不先上 Kubernetes / 微服务。
- 先补可靠性基础：任务提交失败可追踪、broker 持久化与恢复、任务幂等 / 输入保留、刷新并发控制、超时与限流、日志指标和备份演练。
- 再按瓶颈扩容：移除 API 扩容对进程内状态的依赖，多机 worker 改共享 / 对象存储，控制全局供应商并发，协调索引发布和缓存失效。
- 需要更强体验时再做后台持续生成与可靠重放、多轮历史注入、检索融合 / 精排与离线评测；每项都说明收益、成本和验收方式。

**推荐表述：** “现有实现能支撑我验证完整业务链路，但我不会把单机可部署等同于高可用、强一致或无限扩容。”
