# 用户系统交付说明（阶段 2-A：多用户鉴权）

> 本文档记录 ResumeAgent 从「单用户、无鉴权、全局单 Agent」升级为「多用户、JWT 鉴权、资源按用户隔离」的完整交付内容，含设计决策、端点契约、前后端实现、测试与简历要点。
> 接口的唯一真理来源仍是 [docs/specs/api-contract.md](specs/api-contract.md)（§1.2 鉴权约定、§2.1 用户模型、§4.11~4.18 认证端点）；本文是面向阅读者/招聘方的说明与索引。

---

## 1. 目标与范围

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 用户模型 | 无 | `users` 表，email 登录，argon2id 存密码 |
| 会话鉴权 | 无 | JWT access token（Bearer）+ refresh token（httpOnly cookie） |
| 资源归属 | 全局共享 | 对话/消息按 `user_id` 隔离，写路径做归属校验（防 IDOR） |
| 前端 | 直接进主页 | 登录/注册页 + 路由守卫 + 401 自动续期 |

**不在本次范围**：角色/权限（RBAC）、邮箱验证、找回密码、第三方登录。当前仅「本人可改删自己」这一级归属控制。

## 2. 后端设计

### 2.1 数据模型（`src/database/models.py`）

- **User**：`id` / `username`(50, unique) / `email`(120, unique) / `password_hash`(200) / `created_at`。
  - email 强制保留（产品决策），注册与登录都以 email 为凭证，`username` 仅作展示名。
- **RefreshToken**：`id` / `user_id`(FK) / `jti`(36, unique) / `family_id`(36) / `revoked`(bool) / `expire_at`。
  - **不存 token 明文**，只存 `jti`（JWT ID）作为可吊销句柄；`family_id` 把一次登录派生出的所有轮换 token 归为一个「令牌族」。
- **Conversation**：新增 `user_id`(FK, NOT NULL) + `owner` 关系；`messages` 关系 `cascade="all, delete-orphan"`。
- **Message**：归属通过 `conversation_id` 间接挂在用户下（无独立 `user_id` 列）。

> 迁移：`email` 列与唯一约束走独立 revision `fe5a54033dde_add_user_email.py`（`users_email_key`，upgrade/downgrade 对称）。

### 2.2 认证机制（`src/auth/security.py`）

- **密码**：`pwdlib` 的 `PasswordHash.recommended()` → argon2id（哈希以 `$argon2` 前缀，每次加盐）。哈希是 CPU 密集操作，保持普通 `def`（异步只对 I/O 有意义）。
- **access token**：JWT HS256，payload = `{sub: 用户id字符串, exp, type: "access"}`；默认 TTL **60 分钟**（`AuthConfig.access_token_expire_minutes`）。
- **refresh token**：JWT，payload = `{sub, exp, type: "refresh", jti}`；默认 TTL **7 天**。**`family_id` 不进 payload**，只活在数据库里。
- **解码校验**：`options={"require": ["exp", "sub"]}` + 显式校验 `type`，因此 access 与 refresh 不可互相冒用。

### 2.3 令牌轮换与复用检测（jti + family）

刷新时的核心安全逻辑（`POST /api/auth/refresh`）：

1. 用 cookie 里的 refresh token 解出 `jti`，查 `refresh_tokens` 表。
2. **`revoked=True`（旧 jti 被重复使用）→ 判定为令牌泄露信号 → 连坐吊销整个 `family_id` 下所有 token**，返回 401 `Refresh token is revoked`。
3. 正常情况：吊销旧 jti、以同 `family_id` 插入新 jti，下发新 access + 新 refresh cookie（轮换）。

一次登录 = 一个新 family；family 内单次只有一个活跃 jti，任何历史 jti 复用都会引爆整族失效。

### 2.4 refresh token 载体：httpOnly cookie

- `Set-Cookie: refresh-token=<JWT>`，属性：`HttpOnly` / `Path=/api/auth` / `SameSite=Strict` / `Max-Age=refresh_token_expire_minutes×60`。
- dev 环境 `secure=False`（本地 http）；**生产必须置 `secure=True`**（见 §6）。
- `Path=/api/auth` 把 cookie 限制在认证端点，业务接口不会无谓携带。
- **logout 不清 cookie**：服务端把 family 全部 `revoked=True` 后，cookie 里的 token 已是死票，再刷新必 401，无需客户端删除。

### 2.5 归属校验（防 IDOR）

多用户系统里，凡接收客户端资源 id 的写路径都要问「这是不是他的」：

- `POST /api/chat`：`check_conversation(conversation_id, current_user.id)` —— 存在性判据升级为**归属判据**（`WHERE id=? AND user_id=?`），查不到统一 404（不泄露资源是否存在）。
- `GET /api/conversations/{id}/messages`：`conv is None or conv.user_id != current_user.id → 404`。
- `PATCH/DELETE /api/auth/{user_id}`：`user_id != current_user.id → 403`。

### 2.6 端点清单（`src/api/routers/auth.py`，前缀 `/api`）

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| POST | `/api/auth/register` | 否 | 注册，201 `UserPrivate`；username/email 重复 → 409 |
| POST | `/api/auth/login` | 否 | email+password 登录，200 `Token` + Set-Cookie；失败 401 |
| POST | `/api/auth/refresh` | 🍪 cookie | 换新 access + 轮换 refresh；见 §2.3 三种 401 |
| GET | `/api/auth/me` | 🔒 Bearer | 当前用户 `UserPrivate` |
| POST | `/api/auth/logout` | 🍪 cookie | 吊销整个 family，204 幂等，不清 cookie |
| GET | `/api/auth/user/{id}` | 否 | 公开视图 `UserPublic`（不含 email），404 |
| PATCH | `/api/auth/{id}` | 🔒 本人 | 改 username/email，非本人 403，重复 409 |
| DELETE | `/api/auth/{id}` | 🔒 本人 | 删本人（级联删对话/消息），非本人 403 |

🔒 = 需 `Authorization: Bearer <access_token>`；🍪 = 从 httpOnly cookie 读 refresh token。

**401 矩阵**（`get_current_user`）：缺头 → `Not authenticated`；解码失败/过期/`type≠access`/`sub` 非整数 → 统一 `Invalid or expired token`；token 指向用户已不存在 → `User not found`。刻意不区分「过期」与「非法」，避免给攻击者反馈。

### 2.7 配置（`src/config.py` · `AuthConfig`）

```python
secret_key: str = os.getenv("SECRET_KEY", "")   # 复用 .env 已有变量
algorithm: str = "HS256"
access_token_expire_minutes: int = 60
refresh_token_expire_minutes: int = 7 * 24 * 60
```

`AppConfig.__post_init__` 对空 `SECRET_KEY` **fail-fast** `RuntimeError("SECRET_KEY not set")`——避免密钥缺失时静默退化成「任何人可伪造 token」。

## 3. 前端设计（`frontend/src`）

登录闭环的关键是「access token 短命 + refresh cookie 续期」，前端围绕它做了四件事：

### 3.1 token 内存单例（`api/authToken.ts`）

- access token **只存内存**（模块级单例），不落 `localStorage` —— 刷新页面靠 httpOnly refresh cookie 静默续期，避免 token 被 XSS 从本地存储读走。
- 单独抽模块而非塞进 store：`client.ts` / `useChatStream.ts` 是普通模块，若直接依赖 Pinia store 会与「store 又 import client」形成循环依赖。
- 提供 `setOnSessionLost` 回调，把「会话彻底失效」的跳转动作交给 `main.ts` 接到 router，实现请求层与路由层解耦。

### 3.2 401 拦截 + 单飞刷新（`api/client.ts` · `api/auth.ts`）

- 每个受保护请求自动注入 `Authorization: Bearer <token>` + `credentials:'include'`（带 refresh cookie）。
- 收到 401 → **单飞**（inflight promise，并发 401 只发一次 `/refresh`）刷新 → 成功则**重放原请求一次**；刷新仍失败 → `notifySessionLost()` 跳登录。
- 认证端点（login/register/refresh/logout）走独立的最小 fetch 封装，**不进这套自动重试**，否则会 401→刷新→401 递归。

### 3.3 SSE 开流前续期（`composables/useChatStream.ts`）

`/api/chat` 是受保护的 SSE。流一旦开启无法优雅重试，故开流前调 `ensureFreshToken()`：解 JWT 的 `exp`，若 30s 内到期先刷新再连；无 token 时不主动刷新（交由路由守卫处理）。随后把 `Authorization` 头注入 fetch。

### 3.4 路由守卫 + 登录页（`router/index.ts` · `views/LoginView.vue` · `stores/auth.ts`）

- `/login` 标记 `meta.public`；全局 `beforeEach` 首次导航先做 `initialize()` 静默续期（refresh cookie 换 access + 拉 `/me`）。
- 未登录访问受保护页 → 跳 `/login?redirect=<原路径>`，登录成功后回跳。
- `LoginView` 单页切换登录/注册，Element Plus 表单校验（email 格式、密码 ≥8、username 1~50）。
- `App.vue` 登录页不套导航壳；已登录时右上角显示用户名 + 退出下拉。

## 5. 关键设计决策与理由

| 决策 | 理由 |
|------|------|
| access token 只存内存，不落 localStorage | 降低 XSS 窃取面；刷新页面用 httpOnly cookie 静默续期 |
| refresh token 走 httpOnly cookie 而非响应体 | JS 读不到，杜绝前端脚本窃取；`SameSite=Strict` 抗 CSRF |
| jti + family 轮换与连坐 | 令牌复用即泄露信号，一次引爆整族，限制被盗 token 的可用窗口 |
| logout 不清 cookie | 服务端吊销已让 token 变死票，客户端删不删都不影响安全性 |
| 401 不区分「过期/非法」 | 不给攻击者 oracle 反馈 |
| 归属查不到统一 404（非 403） | 不泄露「资源存在但不属于你」这一信息 |
| email 保留为登录凭证 | 产品决策；username 仅展示名 |

## 6. 上线前 checklist（生产环境）

1. **`SECRET_KEY`**：设为强随机值（`AppConfig` 已 fail-fast，缺失会启动即报错）。
2. **cookie `secure`**：`auth.py` 里 `set_cookie(..., secure=False)` 是 dev 值，生产（HTTPS）须改 `True`。建议后续由环境变量驱动，而非硬编码。
3. **access token TTL**：`access_token_expire_minutes` 当前 60（代码注释「测试完后改为 30」）；按安全/体验权衡定稿。
4. **CORS**：`CORS_ORIGINS` 收敛到正式域名；带 cookie 的跨域场景需 `allow_credentials=True` 且 origin 不能为 `*`（同域部署则无此问题）。
5. **同域部署**：生产用单容器 + Nginx 同域（见 [deploy/README.md](../deploy/README.md)），cookie 的 `Path=/api/auth` 与前端 `/api` 代理路径需一致。

## 7. 简历要点（可直接改写进简历）

- 为 LangGraph + RAG 简历 Agent 从 0 设计并落地**多用户 JWT 鉴权体系**：argon2id 密码哈希、access/refresh 双令牌、refresh token 走 httpOnly cookie（`SameSite=Strict`）。
- 实现 **refresh token 轮换 + 令牌族（family）复用检测**：历史 jti 复用即判定泄露并连坐吊销整族，收敛被盗令牌可用窗口。
- 修复对话/消息接口的 **IDOR 越权**：把「资源存在性」判据升级为「归属」判据（`WHERE id AND user_id`），越权统一 404 不泄露存在性。
- 前端设计**内存态 token + 401 单飞刷新重放 + SSE 开流前到期预判续期 + 路由守卫静默续期**，token 不落 localStorage 降低 XSS 面。
- 用**文件版 SQLite + FastAPI `dependency_overrides`** 打通宿主异步路由测试（规避 Windows ProactorEventLoop 与 psycopg 冲突），后端 364 / 前端 125 测试全绿。
